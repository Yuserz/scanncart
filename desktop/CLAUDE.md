# Desktop app (`desktop/src/`)

<!-- Loaded on demand: Claude Code reads a CLAUDE.md the first time it works in this folder. The root CLAUDE.md is the short overview; `/codebase-notes` loads this file by name. -->

Standard electron-vite three-target layout: `main` (Node, Electron APIs), `preload` (context-bridge), `renderer` (React, sandboxed, no Node access).

- **`main/sidecar.ts`** — `SidecarSupervisor` spawns the sidecar (`spawnFn` is injectable for tests), parses `SIDECAR_PORT=<n>` off stdout line-by-line, and forwards stderr so uvicorn's own log pipe never fills up and blocks the child. It also forwards every stdout line that is *not* the port handshake through an `onStdoutLine` sink, which `main/index.ts` prints as `[sidecar] <line>`: the sidecar's own prints (`app/loops.py`'s `EVENT_LOOP=…` right after the port, the parent watchdog's exit line) were read and dropped, so the loop choice — the one fact a person diagnosing a wedged API needs first — reached a log only when someone ran the sidecar by hand, never when the app launched it, which is the only way it normally runs. The port line is consumed rather than forwarded because the port is already logged as `[sidecar] ready on port <n>`; a `\r` is stripped, since the splitter is on `\n` and Windows writes CRLF. Reports the port and unexpected exits via callbacks.
- **`main/sidecarHealth.ts`** — the failure the process lifecycle cannot see: a child that is still *alive* — still in `tasklist`, still holding its camera — with nothing answering on its port. `SidecarSupervisor` reports `exit` and `main/index.ts` used the port it printed as the proxy for healthy, so both were blind to it, and the renderer is blind by construction: its WebSocket is *established* over the same loopback and stays established, which is why a dead API looked like a frozen app. `SidecarHealthMonitor` probes `GET /api/health` instead and reports only **transitions** — `starting` (nothing asked yet, deliberately not an error, so a healthy launch shows no banner), `ok`, and `unresponsive` after three consecutive failures — with three load-bearing details: probes are scheduled from the *end* of the previous one, so they cannot stack behind a hung sidecar; an answer for a port the monitor has moved on from is discarded, because an in-flight request outliving the child it described is the normal case on a restart; and the failure threshold is deliberately forgiving, since telling an operator to restart a working app is worse than noticing a dead one a few seconds later. `stop()` is what `before-quit` calls. The policy constants live in this module rather than at the call site so that balance is a change someone makes on purpose.
- **`main/index.ts`** — resolves the sidecar's python/script paths relative to the packaged app (overridable via `SIDECAR_PYTHON`/`SIDECAR_SCRIPT` env vars), starts the supervisor on `app.whenReady()`, and kills the sidecar child on `before-quit`. It also owns the health signal: one `probe` that is a `fetch` with `AbortSignal.timeout`, and one `setSidecarHealth` that stores the state and pushes it to every window. Two read paths rather than one, because either alone loses a transition — an `ipcMain.handle('sidecar:health', ...)` for a window that mounts *after* a change (a reload, a second window) and the push for one that is already open — and the same reason the port has both. A child that exits sets the state immediately instead of waiting for three failed probes to agree, and only for a child we did not stop ourselves. Both `sidecar:port` and `sidecar:health` are served here, plus the POS integration's four (`pos:get-state`, `pos:get-config`, `pos:save-config`, `pos:test-connection`), which is where it also constructs the `PosController` — once the sidecar's port is known — and calls `start()` on it, stopping it in `before-quit`.
- **`preload/index.ts`** — exposes `window.api.getSidecarPort()` and `window.api.getSidecarHealth()` (plus `onSidecarHealth(cb)`, which returns its own unsubscribe so the caller's effect cleanup is the listener removal) via `contextBridge`, and the POS integration's four (`pos:get-state`, `pos:get-config`, `pos:save-config`, `pos:test-connection` as invokes, `pos:on-state` as an event listener mirroring `onSidecarHealth`). Those are the *only* main↔renderer bridges, and the rule for what belongs in them is the same one for all of them: a fact about this machine's own processes that the renderer cannot observe for itself. Everything to do with the sidecar (REST calls, WebSocket) goes straight from the renderer to `127.0.0.1:<port>` — Electron IPC carries the port — and everything to do with pushcart-web goes through the main process, because the renderer cannot reach that host at all (no CORS story, and the POS secret must not travel into a page).
- **`main/posConfig.ts`** — the POS integration's configuration, read and written as `pos.json` in `app.getPath('userData')`: pushcart-web's base URL, the shared secret, this counter's `station_id`, and the timing numbers (dwell, settle, minimum confidence, three poll intervals). `stationId` is *configured, not generated* — it is the `id` of a row an admin created in pushcart-web's `stations` table — so from this side it is opaque text that the tablet's screen is the only place to read. Empty URL, secret or station id means **disabled**, which is a state rather than an error: `isPosEnabled` is the single predicate and everything downstream asks it. Two rules live in `save` rather than in a caller: it refuses `commitDwellS <= track_expiry_s` (below that, a replacement track commits while the track it replaced is still open inside the sidecar's expiry window, and one item reads as two — so the save fails with both numbers named) and `insecureBaseUrlWarning` is the one spelling of the TLS rule, shared with "Test connection" because a warning shown in only one of the two places is a warning an operator can save past.
- **`main/cartState.ts`** — the pure half of the integration: `deriveCartState(events, now, bindAt, cfg) → Map<class, {quantity, maxConfidence}>`. **Quantity is the number of a class's tracks open *at the same time*, not the number of tracks**, because the sidecar's tracker routinely ends one track and starts another for the same physical item — a hand passes over it, the customer lifts it and puts it back down — and counting tracks over a window would show one item as two every time that happened. Three rules carry it: an **eligible** track entered at or after `bindAt` (items already on the counter when the session bound belong to nobody) and was seen at or above `minCommitConf`; a track counts over `[entered_at + commitDwellS, end]`, so one that ends before its dwell was detector flicker and never counts; and the quantity is the **maximum concurrency over `[now − removeSettleS, now]`**, so a count goes up once the extra track has dwelt and down only after the lower count has held for the whole settle window — which is also what makes a track swap invisible: the old interval ends at the item's last-seen time and the new one commits later, and the gap between them is shorter than the settle window. A track with `left_at === null` is still open, so its interval ends at infinity (`Infinity`, not `now`: a boundary case a test found, where a track expiring exactly at the settle edge read as closed). Everything is the sidecar's `time.time()` seconds, which is comparable to `Date.now()` because it is the same machine's clock. Classes with a quantity of zero are left out, so an empty map means "nothing on the counter".
- **`main/transferState.ts`** + **`main/transferGeometry.ts`** — the basket's deterministic core (`docs/CART_TRANSFER_SPEC.md`): fresh per-inference observations over three regions (outside / opening / inside) become a confirmed **deposit** or **removal** only after ordered evidence — two sightings on each side, then a held endpoint (`endpointHoldS`, 0.4 s — tuned down from the spec's provisional 1 s at 50–60 fresh inferences a second; the transfer is posted to pushcart-web immediately, `notifyBasketChanged` kicking the orchestrator's tick), with every sighting at or above `confThreshold` — which is the scanner's own `conf_threshold`, not a second number: `PosController` re-reads `/api/settings` every 5 s and pushes it in (`setConfThreshold`), so 0.9 on the scanner means the basket infers nothing under 0.9. A reversal aborts quietly; a class change mid-path, a jump within a region (allowance `maxSideSlop` + `slopPerS` × the time between sightings, so a dropped frame during a swing is motion), two *in-flight* tracks crossing the opening within `concurrentOpeningS` (0.5 s; an item resting on the rim does not count), or a track first seen in the opening goes to **review** instead of the cart. `stitch()` re-keys a lost track's history onto a new tracker id of the same class appearing within `stitchGapS`/`stitchMaxDist` (0.6 s / 400 units), never onto an id still in the frame — `BasketTracker` passes the frame's live ids — which is what keeps a brisk swing that blurs the product out of review. A confirmed track's history restarts at its destination, which is what lets "remove, then put back" work on one track without a cooldown — the same direction cannot re-fire because its origin is the side the item just left. v1's regions are **bands** from one frame edge (`presetRegions(cartEdge, insideFraction, openingFraction)`, in a 1000-unit frame, `TRANSFER_FRAME`); drawn outlines (`posConfig.zoneMode: 'drawn'`, for a camera looking down into the basket) are the other `ZoneLayout`, and only `regionOf` (through `pointInZone`) knows the difference. The renderer's **Basket test** screen (`views/BasketTestView.tsx`) draws either layout over the preview, labels each detected box with its product, confidence and track id (HTML over the picture, since the stretched SVG overlay would distort text), edits and saves it, and runs a local *practice* session (`PosController.startBasketPractice`, refs prefixed `practice:`) so the basket counts at a desk with no pushcart-web. `frameBox` undoes the preview mirror with the sidecar's own rule.
- **`main/basketLedger.ts`** — the per-SKU quantities and the event journal in **basket** cart mode: only a confirmed transfer changes a count, so hiding an item never removes it. Each event's id is derived from its facts, so a replay applies zero more times; a removal of something not held is review, never a negative count; review items stay listed until resolved (`pendingReview()` is what the payload's `pending_review` carries); and the file (`basket-ledger.json` beside `pos.json`) is restored only for the same `session_ref`, with a review item because the restart was not watched.
- **`main/transferStream.ts`** — `BasketTracker`, the main process's own WebSocket to the sidecar feeding the machine and the ledger. It reads only `fresh` frames (the sidecar marks preview fill-ins `fresh: false`, since one inference would otherwise satisfy "two sightings" by itself) and only tracked detections, in true orientation (`mirrored` says when to undo the reflection). It owns the two stream-level checks: **blind** (no fresh frame for 2 s, or capture leaving `running`) becomes review when it outlasts a few seconds, and the **empty-basket baseline** flags a product already in the cart band at bind. It is the orchestrator's `BasketPort`, bound and unbound with the session in **both** modes, so counter mode carries it as a shadow readout (`PosState.basket`) for comparison before anyone switches `cartMode`.
- **`main/posSession.ts`** — the orchestrator: its own loop, every dependency injected, so the whole thing runs against fakes with fake timers. It keeps **capture running rather than starting it per customer** (~37 s of device open per *Start*, otherwise), which is why binding is a timestamp: it polls `GET /api/pos/session` every `unboundPollMs` while unbound and every `sessionPollMs` while bound, binds on a new `session_ref` and sets `bindAt = now`, and unbinds when the server reports no session or a `paid` cart — while leaving capture alone. While bound it fetches `/api/logs?since=<bindAt>` every `logsPollMs` into a cache keyed by `(session_id, track_id)`, derives the map, and posts only when it changed, plus a 15 s heartbeat so the webapp can tell liveness from silence. Two guards are load-bearing. The **warm-up** holds the snapshot at the per-class `max(lastSent, derived)` until capture has been running continuously for `commitDwellS + removeSettleS`: a capture restart leaves the camera blind for longer than the settle window, and without the hold the derived state would fall to zero and the camera would post an empty cart for items still sitting on the counter — no snapshot is ever *derived* from a capture that is not observing. And the **sidecar-session change** closes every open cached track at the last time the sidecar confirmed it, so tracks a restart abandoned expire through the settle window instead of counting forever. Failure policy: a webapp error keeps the last counts and surfaces the message, and is the only thing that backs the tick interval off — a doubling per consecutive failure (`RETRY_BACKOFF_CAP_MS` caps it, so a long outage still probes; one clean tick restores the poll cadence), because an outage retried at the poll cadence is a request flood, while capture trouble is `ensureCapture`'s own throttle and a `409` is a session that is over rather than a retry. A `409` means the session is over, so it unbinds; a capture that is not `running` gets **one** auto-restart (a `409` from `/api/capture/start` is calibration in progress, which waits rather than counting as the failed attempt) and then stays bound with the warm-up guard holding the cart where it was, because corrections happen on the tablet. `emit` reports `PosState | null`, where `null` is *there is no integration to report* — the feature is off — rather than an idle-looking state, so the Live view shows nothing for a feature nobody turned on (the same shape the inference verdict uses for "no server to watch"). The loop is started by `start()` (once, when the sidecar's port arrives) **and by `refreshConfig()`**: the Admin Panel's Save is the only way a station gets configured, and the app never calls `start()` twice, so without that a station entered after launch would be saved, reported as enabled, and then sit idle until the next launch. One chain is kept by a `looping` flag, checked in both places and cleared by a tick that finds the feature off (which is also how switching it off stops the polling). The backoff is readable: `PosState.retryAtMs` carries the standing retry's deadline, written only at the tick tail while consecutive failures stand and cleared — with an emit, because a success that changes nothing would otherwise never tell an open window — by the first tick that succeeds. The errors it clears are labelled (`errorSource`): the session poll answers for *both* transports, so a webapp answer clears a webapp or sidecar error but not a capture error, which no webapp answer can see.
- **`main/pos.ts`** — the Electron half: the real dependencies behind the orchestrator (sidecar REST on `127.0.0.1:<port>`, pushcart-web over the configured base URL), the config store, the state push over `pos:state` to every window, and "Test connection". That last one is the Admin Panel's read: it asks for this station's session once and reports the HTTP status, whether a session is open, the cart code, the TLS warning and the sidecar's **live** `track_expiry_s` (`GET /api/settings`, falling back to the default), so the dwell rule is checked against the number that is actually running rather than against the default this build happens to ship. Its `404` and `401` sentences name the fix (register the station; re-copy the secret) because they are the two failures an operator causes and can undo.
- **`main/posClient.ts`** — the wire, split out of `pos.ts` because that module imports `electron` and this one has to be drivable over a real socket. It owns the two desktop-facing routes (`/api/pos/session`, `/api/pos/sync`), the `x-pos-token` header, the JSON snapshot, and the status-code mapping that is the whole contract: `409` → `PosConflictError` (the session is over), any other non-ok → `PosTransportError`, and — the part that was missing — a **refused connection** wrapped into `PosTransportError` too, since `fetch` throws a bare `TypeError` and that is exactly the failure the smoke test spends a row on, with nothing to catch it by. `probePosSession` is the odd one out and never throws: "Test connection" renders a result, so a failure there is a value. `pos.ts` keeps only the Electron wiring (the config store, the state push, the sidecar reads) and hands these three the stored connection details.
- **`main/posRoutes.integration.test.ts` + `main/posWebappStandIn.ts`** — the smoke test's §3 rows the desktop owns, over a real socket. The stand-in is a loopback server faithful to pushcart-web's *routes* rather than its database — its `x-pos-token` check, its `validate()`, `pos_reconcile`'s `{results, cart_totals}` body, and camera rows keyed by class so a repeated snapshot cannot duplicate one — and the test drives the real transport and the real orchestrator at it, with only the sidecar faked. The protocol checks (auth, an unregistered station, snapshot validation, a session that is not open, a 500) are **shared** and run against either host; the lifecycle rows that need control a real server cannot be given (a dead host's backoff countdown, the host coming back with no duplicate rows, a `409` that unbinds, the paid-cart unbind) are stand-in-only. The shared half is why the target exists: `make verify-pos-routes` points it at a real pushcart-web (`POS_E2E_BASE_URL`/`POS_E2E_SECRET`/`POS_E2E_STATION_ID`), which is the only thing that can catch the stand-in drifting from the routes it mirrors. It is out of `make test` (it needs a running server) and fails loudly — exit 2, naming the three variables — rather than reporting a green skip, and a *half-set* environment is an error in the test file too, because a run against a host it cannot authenticate to would report 401s as the route's behaviour. The routes themselves are pinned by `main/posContract.json` — a contract recorded from pushcart-web's own route source by `desktop/scripts/check-pos-contract.mjs` (its two route paths and their exported methods, the header its routes authenticate with, every `response.ts` helper's status, and `mapError`'s code→helper switch). `main/posContract.test.ts` checks `posClient.ts` and the stand-in against that file on a bare checkout, and `make verify-pos-contract` re-reads the sibling checkout to keep it from going stale (exit 2 when the checkout is absent, exit 1 naming the drifted key). The split exists because neither half can see the other's failure: the integration suite's two sides were written from one reading, so a header that moved in *both* files passes it green, and this is the only thing in the repo that knows what pushcart-web actually answers with. `.github/workflows/pos-contract.yml` is what runs the re-read without anyone remembering to: it checks out pushcart-web's integration branch beside this repo and runs that one target, its own workflow rather than a job in `ci.yml` because every trigger there is *this* repo changing while the drift starts in the other one — so it also runs nightly, a `schedule` in `ci.yml` having the same reach only by making its Electron layout check run nightly too. The branch it watches is a repository Variable (`vars.PUSHCART_WEB_REF`, defaulting to `scanncart-integration`), since the POS routes live off the other repo's default branch until the halves are merged — and because a Variable can name a branch that was renamed or merged away, the ref is proved to exist on the remote *before* the checkout and the checkout is proved to be that branch's tip afterwards, so a branch that moved fails the job naming the ref instead of leaving the guard to read whatever tree the checkout settled for. The same surface is guarded on the other side, where the change is *made*: pushcart-web carries its own `scripts/pos-contract.mjs` and the record it writes beside it, deriving that surface from its own routes by the same rules and failing the PR that moves it, triggered on the paths that can move it and nothing else. Deliberately a second independent derivation rather than one file both repos read — two readings that have to agree also catch the case where this repo's extractor stopped recognising the other's source, which a shared file could not. That agreement is not left as an assumption, because there are two recorded copies and each is checked only against its own source: a change re-recorded on one side satisfies both of those guards while the two repos describe different routes, which is the one failure neither repo can see alone. So `make verify-pos-contract` also compares the two copies key by key — the auth header, the routes, the statuses and the outcome codes, never each record's note, which names a different generating script on each side — and it fails naming the key that disagrees. It is the only place that can: it is the only job holding both trees, and the comparison cannot be a file both repos trust without giving up the independence the pair exists for.
- **`renderer/src/lib/ws.ts`** — `createStreamClient` wraps `ws://127.0.0.1:<port>/ws/stream` with auto-reconnect (so the UI tolerates the sidecar not being up yet) and a structural `WSLike` type so tests can inject a fake WebSocket. It dispatches three message types — `frame`, `status`, and `inference` (the backend's server health, `onInference`) — and `StreamMessage` is the union of the three, so a new type is a compile error wherever the union is consumed rather than a message silently parsed and dropped.
- **`renderer/src/lib/api.ts`** — thin REST client (`health`/`start`/`stop`/`getLogs`/`getSettings`/`updateSettings`/`getSystemInfo`/`getPresets`/`applyPreset`/`getDatasetStatus`) hitting `http://127.0.0.1:<port>/api/*`; `request<T>()` supports `GET`/`POST`/`PATCH` with an optional JSON body.
- **`renderer/src/lib/settingsFields.ts`** / **`lib/settingsDefaults.ts`** — client-side mirrors of the sidecar's `ALLOWED_MODELS`/`ALLOWED_DEVICES` and `Settings` defaults, kept in sync by hand (same tradeoff as the WS contract below) — drives `AdminPanel`'s form and its "Restore Defaults" action. The server's `hot_reloadable_fields`/`restart_required_fields` on `SettingsResponse` remain the source of truth for which fields require stopping capture.

- **`renderer/src/hooks/useSidecarStream.ts`** — the core state hook: wires REST + WS into React state, dedupes detections into a session item log by `track_id` (one row per item, keeping the max confidence seen). On WS open it seeds from `GET /api/logs`, but only when `statusState === 'running'` — this is reconnect recovery, not "load history on launch"; a fresh/idle app starts with an empty log, and `start()` resets the dedup set for a new session. Status messages are read as: the `state` always becomes the toolbar's state, and **any non-empty `detail` raises the error banner** — not only one whose `state` reads `error`. That is the two shapes the sidecar has for the same field (a capture dying mid-session, and the stored reason for one that died before this client connected, where `state` is legitimately `idle`), and `detail` only ever carries an error explanation, so gating on the state would just lose the recovered case. The dismissal is the banner's own button and is not remembered across reconnects, because the sidecar still has the same reason. The `inference` message is held as its own state — `InferenceMessage | null`, where **`null` is not `unknown`**: it means nothing has been reported yet, and neither one renders, which is what stops a native capture (no server to probe, so no verdict ever arrives) from showing a permanent notice. It is replaced whole on every inference message, so recovery clears it, and it is deliberately *not* cleared by a capture starting or stopping: unlike `class_names` it describes the configured backend, which a start/stop does not change.
- **`renderer/src/hooks/useDatasetStatus.ts`** — reads labeling progress for the Admin Panel. Loads **once**, not on a timer: the sidecar serves a snapshot file that only changes when the tool is run by hand, so an interval would refetch identical bytes and imply a liveness the data does not have. Exposes `refresh` for a button instead, and the panel renders `age_seconds` so the operator can see the staleness.
- **`renderer/src/hooks/useSidecarSettings.ts`** — fetches settings/system-info/presets on mount and polls `GET /api/health` (reusing the existing endpoint rather than a second WebSocket) to track `captureState` for save-gating. Exposes `update`/`applyPreset`/`restoreDefaults`.
- **`lib/resizeMode.ts`** — `resizeModeMismatch(mode, selectedModel, installed)` is the one place the "settings contradict the weights' record" comparison lives, and both views call it: `AdminPanel` passes the *pending* draft value (so the warning clears as the fix is typed) and the Live view passes the running one. It resolves `auto` through the sidecar's own `auto_resolves_to` rather than reimplementing `resolve_resize_mode`, which is why `auto` can never be the mismatch, and it answers `null` for a weight with no record (a hand-copied file is not mismatched with anything, and a warning no setting could clear is worse than none). Two copies of this comparison would eventually disagree about what "mismatched" means.
- **`hooks/useResizeMismatch.ts`** — fetches exactly the two things the question needs (`/api/settings` and `/api/models`), once, with no polling, and returns the mismatch or null. Deliberately not a second `useSidecarSettings` (that hook also loads system info, presets and a camera profile, two of which are device queries, and `CameraTuning` in the same view already fires it — `apiFactory` goes in the effect deps rather than a ref, matching that hook). A failed load leaves `null`: an unreachable sidecar is already visible in the toolbar, and a verdict that cannot be computed must not send the operator to change a setting that is not the problem.
- **`views/LiveView.tsx`** — renders the JPEG preview, detection-box overlay (`lib/overlay.ts` converts normalized boxes to CSS percentages), fps/latency stats strip, and the item log; Start/Stop drives `start()`/`stop()` from the hook. It also carries **`live-resize-mismatch`**, the same resize warning the Admin Panel's Model field shows, gated on `running` and not dismissible: the claim is about the frames and the log on screen, which is not true of an idle view (where the field is one click away in Admin and already says so), and dismissing it would hide the only explanation for detections that are weaker than the model can do. Beside it sits **`live-assumed-geometry`**, the other resize case and the softer one: nothing contradicts anything (the settings are on `auto`, the documented answer), but no record says what geometry these weights were trained at, so `auto` is guessing — and `settings_store.resize_guess`'s entry is the only thing that can say so, since `resizeModeMismatch` needs a record to contradict. Same gate for the same reason, and the two are mutually exclusive by construction (one needs a record to disagree with, the other needs its absence), so they never stack. It renders the entry's `warning` **and** `remedy` verbatim and carries the **same record-it-now button** the Admin Panel has — safe mid-capture, because the mode written is the one `auto` already resolved to, so the detector is not disturbed; that is what makes the view switch unnecessary. `record()` lives in `useActiveWeights`, taking the model and the mode from the entry the sidecar named (so no caller can write something else), re-reading both endpoints after the write, and setting `justRecorded` only when the refreshed answers no longer report the assumption — so the banner clears because the server says the fact is recorded, not because a click happened, and a failed write simply keeps it with its button. The slot the banner vacated then shows a green **`live-recorded`** line whose sentence is shared with the Admin Panel's acknowledgement (`lib/resizeMode.ts`'s `recordedConfirmation`) and whose mode is read back off the refreshed listing rather than echoed from the click. Beside it, ungated by `running`, the stats strip carries **`stat-requirement`**: what the record says these weights were trained at (`requirement (recorded)`) or, dim italic like the recall tile, that nothing recorded it (`requirement (assumed)`) — the banner's fact while idle, which is when someone is deciding whether to start. **`stat-classes`** is the last tile, and the one fact on this strip that describes the *running* model rather than the configured weights: the class count the sidecar reported on the stream, labelled `classes · roster ok` or `classes · N findings` with the sidecar's own sentences in the title, amber when there are findings. It is deliberately *not* inside the gate that hides the geometry tiles for a remote backend — a workflow declares its classes too, and there is no local model description to hide behind — and it renders nothing until the sidecar has read a model's vocabulary, because `0 classes` would be a claim about a head that has not spoken yet. The division from the banner above is the one the geometry tiles draw: the banner is the problem (only when there is one), the chip is the state (always, once known), which is what makes a healthy `8` as visible as a broken `24`. Above the error banner sits **`inference-unresponsive`**, the one notice on this view that is about neither the capture nor the weights: the sidecar has judged the *backend's own server* silent (a `local_api` run where the camera works and nothing is ever detected is its motivating case, since the detector's failure to start is what stops the capture the banner below reports). It is ungated by `running` — the condition is equally true before Start, which is when it is cheapest to act on — and not dismissible, because it is a state rather than an event; it names the two fixes, since nothing in this window can start `local_inference_server.py`, and it renders the sidecar's `detail` verbatim because a bare "unreachable" cannot tell a stopped server from a wrong port. Nothing here probes the endpoint: the sidecar owns that, and every observable this window has (an established WebSocket, a hung fetch) would look healthy. The side rail also hosts `components/CameraTuning.tsx` — the camera controls that can change while capture runs, plus calibration. `SETTINGS_GROUPS[].home` decides whether a group renders here or in `AdminPanel`; it is one list filtered by both views, so a field cannot appear in both or neither — and `settingsFields.test.ts` now pins **both** halves of that, the duplicate case and the forgotten-one case, the latter by checking `DEFAULT_SETTINGS`' own keys (annotated `SettingsPayload`, so the key list cannot drift from the payload it is checked against). The one exception is `detector_backend`, which `AdminPanel` renders in its own `backend-picker` section because it needs radio buttons, a per-backend hint, the API-key and track-expiry warnings and a Test Connection button; it is named in that test's `BESPOKE_RENDERERS` rather than merely left out of the groups, so *rendering nowhere* is always a failure while *rendering outside a group* is always a decision someone made.
- **`views/AdminPanel.tsx`** — hardware info, a dataset **labeling worklist** (the cells still waiting for a box, ranked biggest-first from the local snapshot, rendering the "run the tool" instruction instead of zeros when there is no snapshot, with an explicit Refresh and a staleness line; the order is the sidecar's and the panel does not re-sort it, because the order *is* the instruction — one place deciding priority), plus a separate **capture gap** block listing the Tier A cells still short of their target — kept apart from the class table because those cells are waiting for the camera rather than a label, preset picker (recommended preset highlighted), and a form over the 10 settings fields with inline tradeoff guidance and hot-reload/restart-required badges. Edits are held in local `draft` state until Save; Save is disabled (with a warning) if the pending diff touches a restart-required field while capture is running.
- **`hooks/useSidecarHealth.ts`** — the reading half of the health signal, and the reason it is not derived here: every observable this window has is *established* rather than live (the same WebSocket that stays open when the sidecar stops listening, a hung `fetch` that looks like a slow one), so the main process answers and this renders its answer. It takes **both** a read and a subscription, for the same reason `main/index.ts` serves both: a window mounting between a change and its broadcast would sit on a stale value until the next change, which a sidecar that stays broken never sends, and a subscription alone would miss the state that was already true. A failed read leaves the state alone — an IPC failure is not evidence about the sidecar, and turning one into an alarm would invent a verdict the main process never reported. `starting` is the initial state and is not an error: at launch nothing has been asked yet, and a banner during a healthy startup is how an operator learns to ignore it.
- **`hooks/usePosState.ts`** — the reading half of the POS state, with the same two-path shape `useSidecarHealth` uses (a read for a window that mounts after a change, a subscription for one already open) and the same reason: either alone loses a transition. Its `null` is *nothing to report* — the feature is off, or nothing has been emitted yet — and neither renders, which is what keeps a window that never turned the integration on from carrying a permanent readout of it. Both bridge methods are read through an optional view (`(window.api ?? {})`), because the process boundary is hand-mirrored and additive: a bridge that predates these methods (or the layout harness, which stubs only what it needs) makes this read *nothing* rather than taking the Live view down with it. `PosState` is imported from `main/posSession` as a type rather than restated, so the wire's vocabulary and the loop's are one fact — the renderer and the main process are the same toolchain, unlike the sidecar's contract.
- **`components/PosPanel.tsx`** — the Live view's read-only POS readout: the phase (`no session` / `warming up` / `syncing` / `error`), the cart code (first 8 characters — the tablet displays the whole one, and the prefix is enough to tell two carts apart), the item count pushcart-web currently totals, and how long ago the last snapshot was posted, with a sync error under them. It renders **nothing at all** when `usePosState` reports `null`, which is the state most windows are in: the rail is a fixed height budget (see `verify-live-layout`), and a readout of a feature nobody turned on would spend some of it on nothing. While a backoff stands it adds one `retrying in Ns` line, counted down *locally* (`useRetryCountdown` against the deadline the state carries): the main process emits on transitions only, and one `setInterval` per deadline is cheaper than one IPC message per second for a number only this line reads. Nothing on it controls anything — the tablet's *Start* is what binds the desktop — so there are no buttons to leave out.
- **`components/PosAdminSection.tsx`** — the Admin Panel's POS section: the base URL, the secret, the station id (pasted from pushcart-web's station list) and the six timing numbers, with Save and Test connection. The config and the connection test both live in the main process, because the renderer cannot reach the pushcart-web host and the secret must not travel into a page; this renders what those report, including the TLS warning verbatim. An empty URL, secret or station id is described as *off* rather than as an error, and a bridge that cannot answer leaves both buttons disabled rather than saving a config nothing read.
- **`components/AppShell.tsx`** — owns Live/Admin view-switching state (`useState`, no router dependency) and renders a small nav, plus the **`sidecar-unresponsive`** notice when `useSidecarHealth` reports the sidecar has stopped answering. It sits above the views rather than inside one because it is about neither: with no sidecar answering, both panels fail (the Live view on frames and the item log, the Admin panel on every read and write), and the reason has to be legible somewhere that does not depend on either view's own request succeeding. Deliberately not dismissible — it describes a condition that is still true, and every other reading on screen is either stale or a failed fetch it explains — and it names the recovery, because nothing in this window can perform it: the port the renderer holds is only good while its sidecar is listening.
- **`App.tsx`** — polls `window.api.getSidecarPort()` until non-null (the sidecar reports its port asynchronously after spawn), then mounts `AppShell`.

The hand-kept sidecar ↔ desktop contracts and the guards that check them are in [`../sidecar/tests/CLAUDE.md`](../sidecar/tests/CLAUDE.md).
