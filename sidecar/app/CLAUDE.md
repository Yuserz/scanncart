# Sidecar runtime (`sidecar/app/`)

Module-by-module notes for the Python service: what each owns, the invariants worth knowing before touching it, and the measurements behind its defaults.

- **`main.py`** — `build_app(state_factory)` builds the FastAPI app. All sidecar state (settings, active pipeline, WS clients, logging store, current session) lives in a single `AppState` dataclass instance closed over by the route handlers — there's no global state. Routes: `GET /api/health`, `GET`/`PATCH /api/settings`, `GET /api/system-info`, `GET /api/presets`, `POST /api/settings/preset`, `GET /api/cameras`, `GET /api/models`, `POST /api/models/record`, `POST /api/detector/probe`, `POST /api/capture/start`, `POST /api/capture/stop`, `GET /api/logs` (with an optional `?since=<seconds>`, which drops tracks that had already left before it — the one additive change the POS integration asked of the sidecar, and what makes the desktop's per-sync payload the size of one customer's session however long capture has been up), `GET /api/dataset/status`, `WS /ws/stream`. `source_factory`/`detector_factory` on `AppState` are the injection points tests use to swap in fakes. `POST /api/detector/probe` builds the detector through that same factory and, for the remote backends, sends a frame **shaped like the capture** rather than a 64×64 square — an aspect mismatch cannot show up on a square — then reports the `sent_size`/`reported_size` pair the detector recorded (read with `getattr`, because that record is a remote-detector extra rather than part of the `Detector` protocol, and the native path leaves both null: its geometry is a settings fact, not something a call discovers). **`WS /ws/stream` sends the current capture state as its first message on connect**, before anything streams: until that existed the only status messages a client ever received were its own start/stop responses and pipeline errors, so a renderer joining an already-running capture (a reload, a second window) showed `idle` over live frames and skipped its `/api/logs` recovery, which is gated on `running`. Three consequences worth knowing: any client's first message is now a `status`, not a frame (sidecar tests use `tests.next_frame()` to skip it); the renderer seeds that recovery from the handshake *or* from `onOpen` — the state usually arrives after the socket opens, so `useSidecarStream` needs both, latched to one `/api/logs` call per connection; and the handshake carries a **`detail`**, because `state` alone cannot describe a capture that *died* before this client arrived — teardown leaves `idle`, which is exactly what a capture that was never started looks like, so `AppState.last_error` stores the pipeline's own sentence (`"Capture stopped: …"`) on the way out and the snapshot sends it. The handshake carries **`class_names`/`class_warnings`** for the same reason: `Pipeline` hands the model's class names up once, `_on_class_list` stores them, judges them (`app/roster.py`, against the roster of the running weight's own generation — `models.generation_for` — and by the names alone when the backend is remote, since a record describes the `.pt` beside it and no such file is what runs) and broadcasts the pair, and a client joining an already-running capture is therefore told the model predicts 21 classes instead of having to infer it from the labels going past. It broadcasts **unconditionally**, which reversed an earlier rule ("a clean list is not news"): the names are also a readout — the Live view's stats strip shows how many classes the running model has — so staying silent on a healthy capture would leave that chip absent on exactly the models that are fine. Both fields are cleared with the rest of the runtime in `_teardown_capture`, since neither describes anything once nothing is loaded. It is cleared *before* `state.pipeline.start()`, not after: the error handler runs on that thread, so a detector that fails on its first frame can record its reason before the next lines run (and an `_acquire` failure raises before that point, leaving the stored reason alone). The third thing the handshake carries is the **inference watch's verdict** (`app/inference_health.py`), as its own message type rather than two more fields on the status: it is a fact about the *configured backend* rather than about a capture, equally true before one starts. `build_app` builds the `AppState` first and then hands a `lifespan` to `FastAPI`, which starts the watch (`_start_inference_watch`) on the way up and stops it on the way down; the watch is *retargeted* from `_apply_settings_patch`, so changing `detector_backend` or the URL moves the probe instead of leaving it pointing at the server the settings no longer call — and it moves to *nothing* for `native`, which has no endpoint to watch. Verdicts are pushed to every connected client, and `_inference_message` is the single spelling used by both the push and the handshake so one state cannot be described two ways. The verdict's *body* (`_inference_payload`) is shared with a **third** surface, `HealthResponse.inference`, because the Admin Panel's question is different from a client's: the panel sits beside the backend fields and renders the evidence — which address is being probed, the failure in the endpoint's own words, **how long ago it was checked**, and the command that would start it — and that last fact cannot come from a push at all, since the transitions-only rule means nothing is sent while a verdict stands. So `GET /api/health` recomputes the age on every read, and `_current_inference_status` supplies it: the running monitor's own status rather than `AppState.inference_health`, which is only replaced when a verdict *changes*. The two cannot disagree about the state (the stored one is a prefix of the same history) and differ in exactly one field — `checked_at`, re-stamped on every probe, including the ones that merely re-confirm a standing verdict — which is why reading the fresh copy is what keeps a server that has been down all afternoon from being reported as un-checked since the afternoon. That fresh copy is what the handshake sends too, so the age means one thing everywhere: this verdict was last probed N seconds ago. The **remedy** rides on the same payload, for the same reason the age does — neither surface can supply it. `local_server_command` is written by the sidecar (`inference_health.local_server_command`), the only side that knows where this checkout is and what platform it is on, and it is the command `docs/DETECTOR_BACKENDS.md` §7a prints: the local server's own venv, never a bare `python`, which is the interpreter that cannot import it. `None` is sent for a verdict that is not `local_api`'s — a command for a backend that does not call that server would be the notice sending an operator to start something this app never uses — and for a checkout with no `.venv-inference` yet, where the notices name the setup step rather than a command that would fail. It is resolved through `AppState.local_server_command_factory` per payload instead of once, so the venv an operator creates after reading the notice is picked up by that same notice. The route sends the message as the **second** message, right after the status snapshot: `TestClient(app)` used without a context manager does not run the lifespan, which is what keeps the rest of the suite free of a background timer, and it is why a client in those tests sees the status alone. Settings patches are always applied via `_apply_settings_patch()`, which `setattr`s onto the existing `Settings` instance (never replaces it — `Pipeline` holds it by reference) and rejects (`409`) changes to `RESTART_REQUIRED_FIELDS` while capture is running.

  Capture lifecycle has five invariants worth knowing before touching it. **Acquisition runs in a threadpool** — `source.open()` blocks for ~37 s on a StreamCam, and inline it froze the event loop so `/api/health` and the WS handshake stopped answering. **The detector and the camera are built concurrently** — the detector factory is submitted to a worker before `source.open()`, so the ultralytics import overlaps the device open instead of stacking after it. Because they overlap, either can fail while the other is still building, so `_acquire` resolves both before returning anything and releases whichever one succeeded; abandoning the future would strand a fully loaded model (VRAM on CUDA) on every failed start. **Teardown goes through `_teardown_capture()`**, which claims and clears the pipeline/source/detector/session under `state.teardown_lock` in one step, because the HTTP stop handler and the pipeline thread's own error handler race here; the thread join happens *outside* the lock, since the error handler runs on the pipeline thread and holding it across a join would deadlock (that path passes `join_thread=False`). **Start reports `running` as soon as the pipeline thread is up** — no first frame is awaited, so a camera that opened but never delivers reads as a successful start for the ~3 s it takes `CameraCapture` to declare the device dead, at which point the WS `error` status carries the explanation. **Frame sources expose `release()`, not `close()`** — detectors are the ones with `close()`; `_release()` handles both.
- **`camera.py`** — `CameraCapture` owns an OpenCV `VideoCapture` and runs a background thread writing into a `LatestFrameBuffer` (a lock-guarded size-1 slot: newest frame always wins, no queue buildup/backpressure). `FakeFrameSource` is the test double. `set_controls()` queues control changes for the capture thread rather than writing them inline: `cv2.VideoCapture` is not thread-safe and `_loop` is calling `read()`, so a `set()` from the FastAPI request thread would race it. Changes are coalesced into a dict, so a fast slider drag costs one write. A queued `None` is **not** a skip, though it used to be one, and the difference is the whole of a bug the operator can see: the device is still holding whatever this app last wrote there, so a setting that goes back to null reads as "auto" while the picture stays exactly where the drag put it. What a reset can actually hand back is one control, and why is worth knowing. `CAP_PROP_AUTOFOCUS=1` asks for the *lens's own* focus — a mode this app can name without knowing what the lens was doing, and the one place reading the device would have been actively wrong, since `CAP_PROP_AUTOFOCUS` answers 0 while the lens is in that mode (measured), so restoring what it read would pin focus on the way to undoing the drag. The other three have no mode to ask for: OpenCV has no automatic brightness at all and this repo has never measured the constants `CAP_PROP_AUTO_EXPOSURE` takes on this backend, so the only undo left would be the value the device held *before* the write — and asking the streaming handle for it is worth not repeating, because the wrong answer sticks. Measured: `get(CAP_PROP_BRIGHTNESS)` said 0.0 over a normal mid-grey picture, writing that "restored" value back turned the picture black, and neither a capture restart nor a reopen cleared it — a reopen does not reset a UVC control this app wrote, which is also what `camera_caps` assumes when it reopens to recalibrate. So a reset of those three stops this app writing the control, and the device keeps the last value it was given until something writes it again: calibration, another program, or a replug. `open()` is untouched by all of this — a null setting still writes nothing, which is what keeps a fresh capture from imposing a value the operator never chose. A device that refuses a value sets `control_error` and keeps streaming — `_loop` has no handler above it, so letting the write raise would kill the capture thread with `failure` unset, freezing the feed with nothing to explain it. `_default_capture` pins `cv2.CAP_MSMF` on Windows deliberately (the StreamCam delivers 60 fps at 1080p over MSMF versus ~15 fps over DirectShow) and drops to OpenCV's auto backend only when MSMF can't open the device at all — so don't "helpfully" switch a misbehaving camera to DSHOW. `_loop` gives a stalled read `FAILURE_TIMEOUT_S` (3 s) as a deadline rather than a retry count, so how long a user stares at a frozen preview doesn't depend on the backoff, then sets `failure` and stops the thread; `Pipeline.process_once` raises that and `main.py`'s `on_error` reports it as an `error` status before tearing capture down. `open()` returning True is **not** evidence of a working camera: the MSMF wedge opens cleanly and then never delivers a frame (symptoms and recovery in the `run-desktop` skill), so nothing should gate on `isOpened()`. **Auto exposure is the app's own** (`AutoExposure`, `camera_auto_exposure`, on by default, hot-reloadable): the StreamCam's built-in automatic exposure lengthens the shutter indoors and was measured settling at 12 fps with a washed-out picture, so the loop holds the shutter at `exposure_cap_for(capture_fps)` (−6 at 60 fps), steers mean luminance to 130 with *brightness* (measured 19→152 across brightness 64→255 at −6, fps unchanged), and only shortens the shutter, never lengthens it past the cap. It runs on the capture thread from a sparse luminance sample every 0.2 s; while it is on, `camera_brightness`/`camera_exposure` are only its starting point (a manual drag is not written), and switching it off writes them back. **Too dark is a state, not a brightness**: on this camera brightness is a black-level offset and gain is not honoured over MSMF, so in a room too dark for the −6 shutter (measured at 04:30: mean luminance 1) raising brightness only painted the picture a flat grey card (contrast — the sample's standard deviation — 2.3, against 24–33 for a lit scene), which the model then read phantoms off. So the loop also measures contrast (`frame_levels`), and when the picture is both under target and below `CONTRAST_FLOOR` it stops brightening, drops brightness back to neutral and sets `too_dark`, which `CameraCapture.too_dark` → `Stats.too_dark` → the Live view's `live-too-dark` notice turns into "add light". `camera_auto_exposure_slow` (off by default, hot) lets it spend one stop of shutter (`slow_cap`, 30 fps at 60) first, and it returns to the cap only with light to spare (`_SLOW_EXIT`, twice the target's floor) so it cannot ring between the two rates.
- **`camera_caps.py`** — measures what a camera can actually do, and now what values to set. Nothing here trusts `cap.get()`: on this hardware, setting `CAP_PROP_EXPOSURE` moved delivered framerate from 12.3 to 30.3 fps while the getter kept returning the old value, so a control counts as supported only when the image or the frame rate visibly changes. `probe_controls()` is destructive by design — it leaves the device holding whatever value it wrote rather than reading a value back through the same lying getter to "restore" it — so `calibrate()` reopens the device before using it further. `calibrate()` then runs `probe_controls` (which controls the device honours) and `sweep_controls` (what to set them to) in a fixed order: autofocus off, exposure onto `BRIGHTNESS_TARGET`, focus for the sharpness peak, brightness to trim the remainder. Order is a dependency — a focus value written under a live autofocus is hunted away from, and sharpness is unmeasurable on a frame that is blown out or black. `exposure_ceiling()` computes the longest exposure that still clears the fps floor arithmetically, rather than discovering that cliff by walking the search off it. `CameraProfile.measured` records the evidence (value, metric, baseline, reached) separately from `recommended`, which is policy — that split is what keeps `camera_derive` pure and re-runnable against a stored profile. `ControlSupport.autofocus` is measured the same way (`probe_autofocus`, watching whether a pinned focus value holds under `CAP_PROP_AUTOFOCUS=0`) rather than inferred from other controls working. `sweep_version` is 0 for profiles written before the sweep existed. An empty `recommended` with `sweep_version: 0` means "never measured" (recalibrate to find out); the same empty `recommended` with `sweep_version: 1` means "measured, and this camera answered nothing" (recalibrating won't help) — opposite operator actions the field exists to distinguish, since neither state can be inferred from the other.
- **`camera_search.py`** — `search_to_target` (binary, for a monotone curve) and `search_for_peak` (ternary, for a unimodal one). Pure and device-free: `probe` is a callable the caller supplies, so the algorithms are tested against synthetic response curves rather than a camera. Two algorithms because the two curves differ — brightness rises monotonically with exposure, while sharpness peaks at the subject's distance. `SearchResult.span` is the flat-curve detector: a sharpness sweep that moves nothing means nothing was in frame, which is reported rather than resolved into a confident wrong answer.
- **`camera_derive.py`** — turns a `CameraProfile` into a settings patch, pure and total so it can be tested against hand-written profiles and re-run against a stored one. Prefers `profile.measured[k]` — a real observation — and falls back to the old flat-boost constants only for controls no sweep ever measured (an un-swept profile, or one the device ignored). `camera_autofocus` is proposed only when `controls.autofocus` measured true, and `camera_focus` is withheld entirely when it's false, since a lens that won't hold a lock just wanders off whatever value is written.
- **`inference.py`** — `YoloDetector` wraps `ultralytics.YOLO(...).track(..., persist=True)` for detection + multi-object tracking (stable `track_id`s across frames) and normalizes results to 0–1-relative boxes via `normalize_detections`. `RoboflowRemoteDetector` satisfies the same `Detector` protocol over HTTP: it downscales before transmit, filters by confidence client-side (the workflow declares no parameters), normalizes against the image size the server echoes back, and assigns track ids locally *only* to detections the response didn't already track. It also keeps `last_geometry`, a frozen `RemoteGeometry(sent, reported)` recorded on **every** call (set before the no-predictions return, or a probe — which always sends a blank frame — would never populate it): `sent` is what `_encode` transmitted and `reported` is the response's `image` block, with `None` meaning the response carried none at all. That third state is why it is a record rather than a number: with no block the detector *assumes* the coordinates are relative to what it sent, and `POST /api/detector/probe` reports both so an operator can catch a workflow that re-frames the image before the model sees it — the remote analogue of `resize_mode_resolved`, and the only geometry fact available when the weights live inside someone else's workflow. The downscale keeps the aspect ratio deliberately: a uniform scale commutes with whatever the model does next, so `remote_infer_size` decides detail rather than object scale, and a non-uniform one would warp objects before they left the machine. It is also the only detector that can be *shed*: `RoboflowRemoteDetector.infer` catches `RoboflowShed` and answers that frame with no detections plus `last_shed = True`, because the server is up and the recovery is another frame's attempt rather than an ended capture — which is what letting it propagate did, since a remote error out of `infer` shuts the pipeline down. The tracker is deliberately not advanced on that frame: a refusal is not an observation of an empty counter, and sweeping expiry on it would expire tracks for the time the server spent refusing. `last_shed` is per call, not sticky, so the flag stops the moment a frame gets through, and it is read with `getattr` because it is an extra rather than part of the `Detector` protocol.
- **`acceptance.py`** — the single owner of the accept/reject decision: `accept_detections()` applies every rule that can decline a detection — the class allowlist, the frame-clamp filter (`suppress_clamped_detections`) and the frame-filling filter (`suppress_frame_filling_detections`) — in that order, returning the survivors plus a per-reason count, and `Pipeline.process_once` asks it once so the overlay, the item log and the store cannot disagree about what survived (the accepted list is the only thing that travels past it). The two shape rules are one measurement read at two thresholds — `pinned_edges()` counts how many frame edges a box sits within `CLAMPED_EDGE_TOLERANCE` of, `is_clamped_to_frame` is four and `is_frame_filling` is three — so the second is the first one's blind spot rather than a different idea: on live frames with nothing placed, the model returned one box covering ~96% of the image as Bear Brand at 0.90-0.94, pinned to the top, right and bottom edges and stopping ~5% short of the left. The frame-filling rule ships **on** (`suppress_frame_filling_detections`), because a default is the only version of a fix the operator actually gets: on the shipped default an empty counter logged `Bear Brand` at 0.90-0.94 with an item-log row to match, and the setting existed while that happened. The cost is measured and named rather than left as a side effect — over the whole v1 export the rule also drops 252 of 2018 ground-truth-matched detections, and the closest of those to a phantom is a real `lucky_me_pancit_canton_calamansi_flavor` pouch at area 0.972 and confidence 0.966 with three edges inside 1% (`tools/unsure_probe.py`'s cost block names it), held right up to the lens, which is how this project's own capture protocol shoots a product. It stays hot-reloadable so that cost can be undone mid-capture the moment an item held close stops registering, and `tools/clamp_probe.py` forces it off so its own five claims keep describing the clamp rule rather than this one. The rule that removes the phantom without paying that is the model's — teach it the staged hard negatives, which is what v2's dataset is for. A third rule, `is_unsure_phantom` (`suppress_unsure_phantoms`, on by default), covers the two families the pinned-edge shapes cannot see, because both pin only one or two edges: a frame-spanning box (the shape this model takes under the geometry v1's record requires) or a wide band lying on a top/bottom edge, *and* a confidence below `PHANTOM_CONF_CEILING` (0.85) — the pair is what separates them, since the confident member of either shape is a real product (a `safeguard_pure_white_60g` at 0.956 is the same shape as a top-edge band). It was priced over the whole export before it shipped and `tools/unsure_probe.py` re-derives the price from the repo — 6 of 2018 ground-truth-matched detections at the app's operating point (0.30%, against the clamp rule's 36 and the frame-filling rule's 252 on the same population), every one a large box the model was unsure of, at the ceiling whose gap the tool prints. Those four figures are written down **once**, in `MEASURED_COST` in that module: this paragraph, `Settings`' comments beside the three flags and the desktop's own field hints are all checked against that record by `tests/test_cost_figures.py` (which also refuses the retired spellings, so the deleted harness's denominator cannot come back into `Settings`' comments or into a desktop hint shown to the operator — which is where it had been sitting after the tool replaced it), and the tool's own last claim fails a run whose measurement no longer agrees with the record, because nothing in CI can re-measure and so nothing else could notice a moved cost — and it is what makes an empty counter log nothing (a 20 s capture logged 0 item-log rows with it on and 17 with it off, same scene). That same tool is the only thing that can exercise the edge band, which exists only in front of a camera: it runs a live empty-counter window, fails if a shaped detection under the ceiling escapes into what the Pipeline kept, and prints the window's frames, detections and mean luminance beside the verdict instead of failing merely because a quiet counter offered nothing — `make verify-unsure UNSURE_REQUIRE_BAND=1` is the run that insists a band was actually seen. `Acceptance.suppressed` deliberately counts the shape rules and not the class rule, so the Live view's suppressed tile stays a readout of the model rather than of the operator's own allowlist. `CLAMPED_EDGE_TOLERANCE`, `is_clamped_to_frame` and `drop_clamped_detections` are defined here and re-exported from `pipeline.py`, because `tools/clamp_probe.py` and this module's tests read them from there, and a second definition is the drift the move removed.
- **`pipeline.py`** — `Pipeline` runs its own thread (`process_once` in a loop) that: pulls the latest frame, optionally skips frames (`infer_frame_skip`), runs inference, drops detections whose class is not on the hot-reloaded `class_allowlist` (empty = keep everything), then — when `suppress_clamped_detections` is on — drops any detection whose box is pinned to **all four** frame edges (`is_clamped_to_frame`/`drop_clamped_detections`, the shape a prediction takes when the model wanted something larger than the image: 19 of the 25 detections the 50 stored empty-counter negatives produce, against 0 of 60 real product frames), JPEG-encodes a preview (`render_preview`, which returns the JPEG and its boxes together, resized to `preview_height`), logs detections, and pushes a `FrameMessage` via the injected `on_message` callback. Track lifecycle (`entered_at`/`left_at`) is derived here: a track not seen for `track_expiry_s` is considered "left" and resolved in the log; `resolve_open_tracks()` force-closes everything still open on capture stop. The preview mirror lives here too, in the preview path only (`preview_mirror`, default on): capture, inference, the logging store and dataset frames keep the true orientation, because these weights were trained on ordinary photographs and a mirrored input asks them to read reversed text and mirrored brand marks. `render_preview` reflects the image and the boxes together behind one call so the two cannot disagree, and both emit paths go through it — reflecting in only one would flicker the overlay at the inference rate. The clamp filter sits here rather than in `normalize_detections`, where the clamp actually happens, because the detector is also what `audit_recall.py` and `spec_check.py` measure through: a filter inside it would delete the evidence the tolerance was chosen from. That evidence is `CLAMPED_EDGE_TOLERANCE`'s own justification — the sweep of candidate tolerances against the empty-counter detections, the real product detections and v1's training labels — and `tools/clamp_probe.py` is what reproduces it, along with the end-to-end pass that walks both populations through this `Pipeline` with the flag off and on (`--strict` exits non-zero if any of its five claims stops holding). It sweeps and prints its distributions rather than only the shipped row, because two populations that overlapped would make any threshold arbitrary and that is worth seeing; and it makes the operating point explicit, since the counted populations move with `conf_threshold` (25 clamped detections at 0.5, 15 at 0.7, on the same 50 frames). It reports what it dropped as `Stats.suppressed` on the frame message (and a tile in the Live stats strip) instead of removing rows silently, since a suppression leaves the item log looking exactly like a model that never had the defect, and it reports a frame the inference server refused the same way, as `Stats.shed` — the one suppression that is not a decision about detections, since a refused frame was never analysed and so is *also* indistinguishable from a clean counter (the detector's dropped frame is the whole fact, and the tile is where it is legible), and it is a *setting* because ~1.4% of these weights' own training labels touch all four edges — an item that genuinely fills the frame is the case it can mistake for a phantom, and expect it to be the wrong default once v2 ships with the negatives. `infer_frame_skip`, `preview_height`, `preview_mirror`, `suppress_clamped_detections`, `track_expiry_s`, and `class_allowlist` are all read fresh from `self._settings` every call, so mutating them in place on a running pipeline takes effect immediately (no restart) — everything else the pipeline holds (`active_model`, `device`, the camera index and capture size) is baked into `source`/`detector` at construction and needs a stop/start cycle — `conf_threshold` and the camera controls are the exceptions, reaching the live detector and device through `_push_live_settings()`. `_report_class_list()` calls `on_class_list` **once**, with the detector's class names, on the first inference that knows them — not at construction, because `YoloDetector.names` is deliberately empty until then (filling it eagerly would build a second ONNX session) and a check there would call a perfectly good weight one that predicts none of the roster.
- **`dataset_status.py`** — reads the labeling-progress snapshot the dataset tooling writes (`sidecar/tools/label_progress.py` → `sidecar/data/datasets/cleaned-v2/label_progress.json`) and hands it to `GET /api/dataset/status`. Deliberately file-only: the sidecar makes no Roboflow call and needs no key, so the app keeps its offline promise and the roster travels *inside* the snapshot rather than as a second copy here. `available: false` is a 200, not a 404 — "nobody has run the tool yet" is the state the panel starts in — and `generated_at`/`age_seconds` ride along because the numbers are only as new as the last tool run. It keeps its own copy of the workspace path on purpose (a packaged sidecar does not ship `sidecar/tools/`), which `tests/test_dataset_status.py` pins against `tools/workspace.py` — the same file pins its own copies of the pseudo-class slugs, of the split names and of the distance axis (`SPLIT_NAMES`, `DISTANCE_ORDER`), for the same reason. The snapshot also carries Tier A's **capture gap** (`tier_a_*`), sourced by `label_progress.py` from `clean_v2.TIER_A_CELLS` so the panel and the folder skeleton cannot disagree; an older snapshot without the block reads as "no gap" rather than erroring, and `tests/test_dataset_drift_guards.py` pins that the progress tool imports that table rather than copying it. It carries the **capture-session spread** (`sessions`) for the same reason: `label_progress.py` reads the session off each image's tags — not the manifest, which the hard negatives are absent from — and `splits` is *derived* here from the three counts rather than trusted from the file, so the flag the panel colours on cannot disagree with the numbers printed beside it. The panel marks a session only when it sits in both `train` and `test`, which is narrower than the `splits` count on purpose: a session spread across train and valid is the ordinary remainder and does not spoil a test number. It also **derives the labeling worklist** (`labeling_backlog`: the same counts as `classes`, ordered most-remaining-first with finished cells dropped) rather than having the tool write a second list, since `by_cell` already carries every number that needs and a second list in the file could only disagree with the first. A cell is one class at one distance, which is what makes the list actionable in a way a per-class table is not: the thing that stalls a project is a distance bucket nobody opened, not a class nobody started. Two details are load-bearing — `remaining` is `total - decided` computed on read (clamped at 0, so a snapshot claiming more decided than total cannot sort first with a negative), and the hard-negative pseudo-class is appended from `by_class` because its frames carry no distance and so have no cell to sit in, which would be the one omission with a cost (its frames are marked with the annotator's null tool, and an unmarked one never enters a version).
- **`logging_store.py`** — `LoggingStore` is the sole SQLite writer (one connection, one `threading.Lock`, since the FastAPI request thread and the pipeline thread both touch it). Schema: `sessions` (one row per start/stop capture cycle) and `detection_events` (one row per track per session, `max_conf` tracked across the track's lifetime, `left_at` NULL while still in frame).
- **`inference_health.py`** — whether the server the selected backend calls is answering, and the only thing in the app that can explain a `local_api` run where the camera works, the preview streams, and nothing is ever detected. A background thread (started by `build_app`'s lifespan, not per request) probes on an interval and reports only **transitions** — the exact mirror of the desktop's `main/sidecarHealth.ts`, and for the same reason: both halves of this app are blind to a peer that is silent rather than absent. Transitions are the *broadcast*; what the monitor keeps is a **reading**, re-stamped on every probe (including the ones that re-confirm a standing verdict and tell no client anything), because "how long ago was this last checked" is only honest if it keeps being recomputed — a number that moved only on a change would describe a monitor nobody is running. `InferenceStatus.checked_at` carries it and `age_seconds()` computes the age **at read time**, returning `None` (never `0.0`) for a target that has not been probed — the three-state rule this app uses everywhere a missing fact must not read as a value. `retarget` resets it with the state, so the old endpoint's last check can no more be reported under a new one's name than its health can. Three details carry it. `probe_url` counts **any HTTP response as an answer** (no `raise_for_status`, no API key): a 401 or a 404 means something is listening, and only a connect failure or a timeout means nothing is — which is what keeps this usable without a Roboflow key. The target is `(backend, url)` and `retarget()` resets the miss count and the state to `unknown` when it moves, so a verdict about the old server is never shown beside the new one's name (`native`, or an empty URL, is a target of `None` and probes nothing). And a verdict is discarded when the monitor is stopping or the target has moved — an in-flight probe outliving the thing it describes is the normal case on a settings change. `AppState.inference_probe`/`inference_monitor_factory` are the injection points tests use, and the module imports only the standard library besides `httpx` (inside `probe_url`), so it cannot drag the app's runtime into a pure test. `InferenceState` lives here and is imported by `schemas.py` rather than restated, so the wire's vocabulary and the monitor's are one fact. `local_server_command()` is the other thing a notice needs and only this side can write: the line that starts `local_inference_server.py` on this machine (the sibling `.venv-inference` interpreter plus the script), or `None` when there is no such venv — because a checkout that never set the local backend up has to be sent to §7a rather than handed a command that fails, which is what the bare `python` it replaced did on every machine.
- **`schemas.py`** — Pydantic models shared by the WS frame protocol and REST responses (`Detection`, `FrameMessage`, `StatusMessage`, `InferenceStatusPayload`/`InferenceMessage`, `HealthResponse` (whose `inference` block is that payload, so the stream and the polled read cannot spell one verdict two ways — `None` there means *no server to watch*, which the panel renders as nothing), `LogEvent`, `LogsResponse`, `SettingsResponse`, `SettingsUpdateRequest`, `SystemInfoResponse`, `PresetsResponse`, `DetectorProbeResponse`, `CameraInfo`/`CamerasResponse`).
- **`settings.py`** — plain dataclass `Settings` with hardcoded defaults (no env/file loading — stays pure so its own tests never depend on disk state); `resolve_device("auto")` picks `cuda` if torch reports it available, else `cpu`.
- **`settings_store.py`** — `load_settings()`/`save_settings()` persist `Settings` to `data/settings.json` (atomic write via temp file + `os.replace`; a missing/corrupt file or a bad individual field falls back to defaults rather than crashing startup). Also owns `HOT_RELOADABLE_FIELDS`/`RESTART_REQUIRED_FIELDS` (the single source of truth for which settings a running pipeline picks up live) and `compute_warnings()` (soft warnings surfaced in `SettingsResponse`, e.g. an uncommon capture resolution or a frame-skip/track-expiry mismatch). One of those warnings reads the same `resize_requirement`: a recorded `stretch` silences the "stretch on a custom .pt" warning, so a record can overrule the heuristic that warning comes from. The requirement's *absence* is a different case and deliberately **not** in this list — it is `resize_guess()`, a pure function returning a frozen `ResizeGuess(mode, warning, remedy)`, which `_settings_response` turns into `SettingsResponse.unrecorded_resize_mode`. It left the flat list to gain a remedy: `auto` + a custom `.pt` + no record means `resolve_resize_mode`'s letterbox is a guess rather than a fact, nothing can flag it as a mismatch (there is no record to contradict), and `resolve_resize_mode` is too pure to report itself — so the entry carries the mode, the model, and the **two sentences** (`warning`: the diagnosis; `remedy`: how to stop assuming, written to survive being read in a view with no button under it), and the Admin Panel renders a one-click `Record it now` beside them. Prose could not carry that (a remedy is not a string), and reporting it in both places would put the same situation on screen twice, once without an answer. "Both places" means the Admin warning list — the **Live view** renders the same entry too, because it is the screen where weak `far` detections are watched and it is the one screen the mismatch rule cannot serve. The gates live in `resize_guess` so the sentence and the button cannot disagree about when they apply: native-only, matching `resize_mode_resolved`, since a remote backend's workflow holds its own geometry; gated on `auto`, because an explicit `letterbox` is a decision; and the resolved mode is checked rather than inferred, so if the heuristic ever answered something else for a `.pt` this goes quiet instead of contradicting the geometry the detector was built with. The hot set covers more than the fields `Pipeline` re-reads: `conf_threshold` reaches the detector through `set_conf()` and the four `camera_*` controls reach the open device through `CameraCapture.set_controls()`, both routed by `_push_live_settings()` in `main.py`. `PATCH /api/settings?persist=false` applies without writing the file, and `POST /api/settings/save` commits what is in memory. It is also the single owner of the three camera-control ranges (`BRIGHTNESS_RANGE`/`EXPOSURE_RANGE`/`FOCUS_RANGE`): `SettingsUpdateRequest` builds its `ge`/`le` out of them and `camera_caps` imports them, so the API's accepted span and the span the probe may write are one fact rather than a mirrored pair - the panel's sliders are the only reader that cannot import them, which is the guard that remains — that pair is what lets the Live tab's tuning card drag a slider without every intermediate value becoming the startup config.
- **`hardware.py`** — `probe_hardware()` reports CPU count/RAM via `psutil` and GPU name/VRAM via a lazily-imported `torch.cuda` (same `try/except ImportError` shape as `resolve_device()`).
- **`presets.py`** — `PRESETS` (`low_end`/`mid_range`/`high_end`) are partial settings patches an admin panel can apply wholesale; `recommend_preset()` picks one from `probe_hardware()`'s output using simple CPU/RAM/VRAM thresholds.
- **`roboflow.py`** — `WorkflowClient` posts a base64 JPEG to a Roboflow Workflow (one client serves both `local_api` and `cloud_api` — they differ only by base URL). Retries only timeouts/connect-failures/5xx, never 4xx — read apart from those are `SHED_STATUSES` (503/429), the one pair that says the server is *alive and busy* rather than broken: uvicorn answers exactly that when `SERVER_CONCURRENCY_LIMIT` (`app/loops.py`) is reached, so the client waits the refusal out (honouring a readable delta-seconds `Retry-After` as a floor, capped by `RETRY_AFTER_CAP_S`, because a gateway's mistaken `3600` must not stall the frame holding it) and finally raises `RoboflowShed` — its own type precisely so a caller can tell "at capacity" from "server down" and keep running. The wait is unchanged from the plain backoff's own worst case, which is what keeps it inside `track_expiry_s`. Uses `httpx` (already a dependency) rather than `inference-sdk`. The API key goes in an `Authorization: Bearer` header only, and is kept out of `__repr__` and every error message. `find_predictions()`/`find_image_size()` locate the detection list structurally, because workflow output names are chosen by whoever built the workflow.
- **`credentials.py`** — reads `ROBOFLOW_API_KEY` from the environment, falling back to `sidecar/.env`. Deliberately *not* on `Settings`: settings are serialized wholesale to the renderer, so the API exposes only `roboflow_api_key_present: bool` and never the value.
- **`roster.py`** — the app's own copy of the canonical class names **per generation** (`V1_ROSTER` and `V2_ROSTER` are both seven names - Palmolive, the one class v2 ever added, was dropped, so `V2_ROSTER` *is* `V1_ROSTER` and the generation dimension currently buys nothing but is kept because the next added class re-opens it), `resolve_roster()`, the distance-word predicate, and `class_list_problems()`, the pure verdict over a weight's *own* class list. Per generation because the roster is a fact about the dataset that trained the head, not about the app: judged against v2's eight while v2 still held Palmolive, the v1 weights this app runs carried a finding on every capture that no setting or retrain could clear, and a warning nobody can act on is how an operator learns to ignore the ones that matter — while judged against v1's seven, a v2 head that lost a class reads as healthy. `resolve_roster` picks by the evidence available, strongest first: the record's `generation` (the only thing that can settle one generation against another when the names are the same - which they are today, v2's list *being* v1's seven since Palmolive was dropped, so this is the branch that would keep a v2 head distinguishable from v1's the moment a class is added), then an exact match on the class list itself (a model that predicts exactly v1's seven *is* a v1 model, which is what keeps the shipping weight clean with no record beside it and what makes a future generation work with no edit here), then the closest roster, and finally the newest for a list that matches nothing. It exists because a class list is a property of the weights and **nothing else in the runtime knows it**: a `.pt` records no roster, the filename is a convention, and the export that produced it is long gone — so a model trained from a distance-split project loads happily and predicts 21 classes, which the item log then reports as one product under three labels with no error anywhere. That is the other half of the dataset tools' guard (they refuse to *create* such a set; this is what notices one arriving from anywhere else). It cannot import `sidecar/tools/` — `label_classes.SLUG_TO_CLASS` is outside the runtime by design — so the roster and the predicate are a second copy held in step by a **drift guard** (`tests/test_roster.py`), the same hand-mirrored-contract pattern as the settings/WS mirrors. Three findings, worst first and deliberately non-redundant: a distance in a name (the 21-output failure, with the repair named as a retrain, since no setting fixes a head with 21 outputs), names outside the roster, and roster names the model *cannot* predict — that last one is the quiet direction, because nothing it does predict is wrong. It is deliberately silent about the missing-roster finding when a distance is present: technically true, but it restates the same fact in the other direction and would bury the sentence that says what to do. Surfaced on `DetectorProbeResponse.class_warnings` from both probe branches (native and remote — a workflow's model is the one that can change without touching this app), and rendered by the Admin Panel's Test connection result, which otherwise shows only a *count* of classes; a 21-class weight reads there as "21 classes", which looks like a bigger model rather than a broken one. Two further surfaces carry it without anyone pressing anything: the Admin Panel's *Weights on disk* list judges the class list `train_model.py --install` **recorded** beside each weight (`app/models.py`, which also passes the record's `generation`, so a v1 weight is judged against v1's roster), so a bad one is visible before it is even selected, and the Live view's stats strip carries **`stat-classes`** — the running model's class count plus a count of the findings — which is the one place the count is a readout rather than an input to a verdict, so `21` where an operator expects their own model's count is legible as a number. The findings name the roster they were judged against (`this app's v1 roster`), because "the roster" is no longer one list and the sentence would otherwise not say which expectation was missed.
- **`tracking.py`** — `IouTracker` supplies stable `track_id`s for remote backends, which get none from the workflow. Greedy IoU, class-aware (a track never migrates between classes). Pass `expiry_provider` rather than a fixed `expiry_s` when tracking against live settings: `track_expiry_s` is hot-reloadable, so a snapshot desyncs the tracker from `Pipeline` the moment an operator changes it. `reserve_id()` stops a locally-minted id colliding with a server-supplied one.
- **`models.py`** — `installed_models()` answers "what weights could I select, and what does each one need?" by reading `sidecar/models/`, and `GET /api/models` serves it alongside the built-in list. The counterpart to `settings_store.is_custom_model`, which validates model *names* without ever touching the filesystem (so settings tests stay pure) and therefore cannot answer what exists. Exists because the picker was a fixed list in the renderer: a newly trained `models/scanncart-grocery-v2.pt` was valid to the API and impossible to select in the UI, so the one moment the model changed was the one moment the app needed a code edit. Everything it lists is filtered through that same validator, so nothing offered can fail to save; a missing directory is an empty list, not an error. The second half is `read_record()`: the `models/<stem>.json` that `train_model.py --install` writes beside each weight, whose `resize_mode` is the requirement those weights must be run with, whose `class_names` is what they predict, and whose `generation` is which dataset trained them — a `resize_mode` of `None` means *not recorded*, never a guess, and a missing, corrupt or hand-edited record degrades to that rather than raising (the Admin Panel loads this on every open, and a value the settings PATCH would reject is dropped rather than presented as a requirement; a `generation` this app has no roster for is read as *not recorded*, so a record written by a later tool is judged by the names it carries). `class_names` is the read that moves the roster guard *before the run*: `_read_class_names` drops entries that carry no name and answers the empty list for anything absent, and `installed_models` judges a non-empty list with `roster.class_list_problems`, passing the record's `generation` with it — the one caller that has it, and what keeps a v1 weight off v2's roster — so the panel's *Weights on disk* list carries the same sentences the probe and the Live view do about a 21-class head, while an empty list stays silent, because `class_list_problems([])` would report every roster class missing, which is a verdict about a class list nobody has seen. `generation_for()` is `requirement_for`'s sibling for the *capture* path: the native probe and the runtime class-list judge read it, so the roster a running model is held to comes from its own record rather than from a default. It is the second fact only `--install` ever knows (a `.pt` keeps no label set, and the export is the only thing that did), and `record_requirement`'s merge-not-replace is what stops the app-side writer from deleting it. `requirement_for()` is the same record read for the *capture* path instead of the panel: `_default_detector_factory` and `_settings_response` hand it to `resolve_resize_mode`/`resize_guess`, so `auto` **honours** the requirement rather than merely displaying it. `record_requirement()` is this module's *second writer* of those files — the other is `--install`, which knows the requirement because it knows the training run, and this one exists for weights that arrived some other way, where the operator holds the fact; `POST /api/models/record` is its route and the Admin Panel's button is its caller. It merges rather than replaces, because the rest of a record (which dataset version, what `--val` measured) is evidence only a training run can supply, and a whole-file write would delete measurements to add one field; it writes through a temp file + `os.replace` for the same reason `save_settings` does (a half-written record reads as "nothing known", silently discarding the requirement just recorded); it refuses `auto` (a lookup, not a requirement — `resolve_resize_mode` ignores a recorded one, so it would look like the question was answered while `auto` guessed on) and weights that are not on disk (a record describes the file beside it). Its answer is the refreshed `ModelsResponse`, because that list is where the change shows. That is what makes `resize_mode: auto` the correct setting for a locally trained `.pt` — the format heuristic answers `letterbox` for one, which is the wrong geometry for weights trained on a `Stretch to` version, and the failure is silent. `auto_resolves_to` is reported per model for the same reason `hot_reloadable_fields` is: it lets the UI compare the setting against `resolve_resize_mode`'s actual answer instead of reimplementing that rule in TypeScript. With the record honoured it equals the requirement; what it still earns its place for is the *unrecorded* weight, the one case where `auto` really is a format-based guess and the panel has to say which way it falls — the same case `resize_guess` reports, with the one-click remedy beside it, so the guess reaches an operator even with no record to contradict.
- **`cameras.py`** — `list_cameras()` pairs each workable OpenCV index with a Windows device name (PowerShell/`Win32_PnPEntity`, same shape as `hardware.py`) so the Admin Panel can show "1 — Logitech StreamCam" instead of "1". The index↔name pairing is *positional* and can be wrong, which is why each device also reports the resolution it opened at — that is the operator's check. Scanning opens every device and is slow (~30 s), so `GET /api/cameras` caches it and only re-probes on `?rescan=true`, and refuses entirely while capture holds a device.
- **`run.py`** — entrypoint. `bind_port(8765)` binds *and listens* before anything is announced, falling back to an OS-assigned free port if 8765 is taken, then prints `SIDECAR_PORT=<n>` to stdout — this is the handshake the Electron main process parses to learn where to connect. Handing uvicorn a socket that is already listening (rather than picking a port, closing it, and letting uvicorn bind it again) is deliberate: the renderer's one-shot settings load lands the instant the port is read, and a kernel backlog makes that request wait rather than fail. `server_config()` carries both of `app/loops.py`'s choices — the loop and the concurrency bound — and exists as a function so a test can resolve the first through uvicorn's own `get_loop_factory()` instead of trusting either half of the pair.
- **`loops.py`** — which event loop **every uvicorn server in this repo** serves on, and why it is not uvicorn's own choice on Windows. uvicorn picks `asyncio.ProactorEventLoop` there, and that loop's accept path is a self-rearming callback whose `except OSError` branch **closes the listening socket and never re-arms** (`asyncio/proactor_events.py`, `BaseProactorEventLoop._start_serving`): the first aborted connection — a renderer reloading mid-request, a probe cancelled when a window closes — logs `Accept failed on a socket` with `OSError: [WinError 64] The specified network name is no longer available`, and from that moment the process is still alive in `tasklist`, still holding its camera and its threads, while **nothing is listening**: `/api/health` hangs, so does every new request and WebSocket connection, and the renderer sits in front of a dead API until someone restarts the app. Reproduced against this repo's own entrypoint by opening 400 connections and aborting them (`SO_LINGER 0`) before the handshake finished — that traceback, then a health check that never answers with no LISTENING row in `netstat` and the pid still present, which is also the shape of the sidecar that had been unresponsive on 8765 for a whole session while Electron stayed up. The selector loop has no such branch: a failed accept is re-raised into the event loop's own callback handling (CPython's comment is `# The event loop will catch, log and ignore it.`), the reader stays registered, and the same 400 aborted connections cost nothing but lines in the log. `SERVER_LOOP_SETTING` is the choice in the only shape uvicorn accepts it, and it names the **class, not a function returning it**, because uvicorn hands the resolved value to `asyncio.Runner(loop_factory=...)`, which *calls* it — so a factory returning the class kills the process at startup with a missing-argument `TypeError` rather than quietly serving on the wrong loop. What it gives up is small but not nothing, and it is stated as measured: the proactor is the only loop that supports `asyncio` subprocesses and this app has none (the `hardware.py`/`cameras.py` probes are synchronous), while the selector loop on Windows is `select()`, which takes a **count** of descriptors and raises `ValueError: too many file descriptors in select()` past it — 512 in one call return, 513 raise, measured in this venv, straight out of the event loop's scheduler and caught nowhere. The count is of *registered* descriptors, so for a server it is its live connections plus the listener and the self-pipe, and what reaches it is a **flood** rather than a client count: 520 connections opened and held with nothing sent on them ended a real sidecar on the plain selector — `health=refused` afterwards, that traceback in its log — which is why the loop is not the whole answer and `BatchedSelectSelector` exists. It polls in batches of `SELECT_BATCH` (500, under the platform's figure rather than on it) with every batch but the last at a zero timeout, so an arbitrary number of descriptors is still polled, the loop's own schedule is unchanged, and the same 520-connection flood now leaves the server **listening** and answering. It is used only where `select()` is the platform's best option (`DefaultSelector` being `SelectSelector`), so Linux keeps epoll and a heavy app's accepted-socket habits stop being the thing that decides whether the server lives. That batching is what `startup_line()` reports beside the loop for the same reason the loop is reported at all. The proactor, by comparison, dies on the *first* aborted accept — which for a server the sidecar calls under a timeout is an ordinary event — so the trade is a rarer and louder ceiling for a routine and silent death (Linux gets epoll here, which has no such cap, which is why Roboflow's own Docker image never shows this). Three servers serve over uvicorn and all three name these two constants: `run.py` (where it was found), `annotate/run.py` (the labeling pass — hours long, with a browser reloading pages at it, which makes it the likeliest place to abort a connection and the most expensive place to lose the server) and `local_inference_server.py` (called during a live capture). That second and third case were measured rather than assumed: the same ten-second abort storm leaves the annotator `UNREACHABLE` with `listening sockets: 0` and the process alive when its call site omits the loop, and answering with one listener when it names it. The second constant is `SERVER_CONCURRENCY_LIMIT` (64), handed to uvicorn as `limit_concurrency`: past it uvicorn answers `503 Service Unavailable` with `connection: close` instead of working on the request, so a request flood is *shed* rather than queued — a runaway retry loop or a browser hammering a stale tab is turned away in milliseconds instead of holding a socket, a parser and a task. It is deliberately a policy number rather than the platform's, and deliberately well under it, and it cannot cover the flood the selector was fixed for: uvicorn decides at headers-complete and a connection that sends nothing never gets there, so the two halves answer different floods and neither replaces the other. Each entrypoint also **prints the loop and the selector it serves on as it starts** — `EVENT_LOOP=SelectorLoop(selector=BatchedSelectSelector)`, beside the port it already announces, from `startup_line()` here so the three spellings are one. The tests and the code can both be read for the choice, but a server misbehaving on a machine nobody can instrument is diagnosed from its log, and "not the proactor, and not the selector that dies at 513" is the fact a reader needs first. `tests/test_server_loop.py` is the guard, and it asks uvicorn rather than re-importing the setting string: one test resolves the constant through `Config.get_loop_factory()` and requires that class's name to be what `startup_line()` prints, another scans every `.py` under `sidecar/` for uvicorn call sites and requires each *serving* one to name both constants *and* its entrypoint to print the line (parsed with balanced parens, so a wrapped call still reads as one — and so a `loop=` in a neighbouring call cannot vouch for this one; a call in a test resolves a choice rather than serving, and is asked for the loop it also names and not for a bound a config with no app cannot have), a third shows the ceiling without a server by registering 520 descriptors with each selector — the plain one raising, the batched one answering, and a ready descriptor past the batch boundary still reported — and a fourth asserts this module imports nothing but the standard library (`asyncio`, `select`, `selectors`), which is the property that lets the inference server's *separate venv* import it. `tests/test_server_flood.py` is the other half and needs a real server, which is why it is its own module: one test holds 520 silent connections and requires the server to answer afterwards, the other walks up to `SERVER_CONCURRENCY_LIMIT` one connection at a time and requires the connection past it to be uvicorn's own 503 — asserted with a body, since that is what tells a shed connection from an application error — and the next client served once the flood is closed.
- **`../local_inference_server.py`** (outside `app/`) — runs Roboflow's inference server natively so `local_api` works without Docker. Lives in its own venv (`.venv-inference`, `requirements-inference.txt`): `inference` pins numpy/opencv versions that conflict with the ultralytics stack, so installing it into `.venv` breaks `native`. The sidecar never imports it — they only talk over HTTP. It is the one module that imports *from* the app without talking over HTTP: `app.loops` for the event loop and the concurrency bound, which is why that module must stay dependency-free. Its uvicorn call names both, and the import is inside `__main__` because `app` only resolves after the `sys.path` insert at the top of the file (the same order `_load_key` reads `app.credentials` in).
