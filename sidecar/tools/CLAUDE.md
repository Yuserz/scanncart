Not part of the runtime — the sidecar never imports them — but tracked, because they own the v2 dataset convention in `docs/MODEL_TRAINING.md` §8 and `docs/CAPTURE_CHECKLIST.md`. `clean_v2.py` (ingest → dedupe → stage → upload/retag/wipe/sanity, plus `scaffold`, which lays out a capture tier's `<PRODUCT>/<DISTANCE>/` folders, its README and its exact filing commands from the same `CLASS_MAP`/`DISTANCE_MAP` the ingest uses so a hand-typed folder name cannot be silently skipped — those command paths are rendered `as_posix()` on purpose, because the README is pasted into a shell and on Windows `Path.__str__` gives `sidecar\data\...`, where bash eats the backslash as an escape and `clean --src` then ingests nothing from a directory that never existed. For a held-out tier it also prints the **coverage preflight** (`holdout_gaps` over `staged_coverage` of the earlier sets): the cells with no images outside the session, which are precisely the ones `plan_split --holdout-session` refuses on, asked at scaffold time because by then the fix is a camera decision rather than a planning one. It shares the planner's zero-coverage rule by agreement rather than by re-derivation — a test asserts the preflight's list equals `plan_split.summarize`'s `no_train_cells` for the same staged set — and with nothing staged it reports that it *cannot tell* instead of naming all 21 cells — `TierPlan`s `TIER_A` (session s2) and `TIER_D` (session s3, the held-out acceptance re-shoot, whose commands plan the split *between* `clean` and `upload` because a split cannot be set afterwards); Tier D's cells are derived from the roster × the three distances rather than hand-listed, since it exists to re-shoot what earlier sessions cover). Its **capture session** is load-bearing rather than decorative: `--session` is recorded in the manifest and stamped as a third tag (Roboflow's dataset search has a `tag:` filter and no `batch:` filter, so a batch can group images but not select them), `batch_for_session()` is the single rule naming a session's batches and is shared by `upload`, `retag` and `plan_split` — a planner naming batches differently from the uploader would assign splits to batches that never exist — and `retag`'s read-back verifies the same wanted set it applied rather than the manifest's own tag list, `capture_hard_negatives.py` (the producer for the folder layout Tier C2b of the checklist describes and `clean_v2 clean --negatives` ingests - frames off the checkout camera, or any video, as `images/*.jpg` with empty `labels/*.txt` beside them, numbering continued across runs rather than overwritten, and the declaration written under `workspace.DATA_YAML_NAME`. Two details are the repo's rather than the camera's: it opens the device through `app.camera._default_capture` instead of `cv2.VideoCapture` directly, because a negatives set shot through a different OpenCV backend is a set of frames from a camera state the model never meets at runtime, and its closing advice points at the v2 route - stage with `--negatives`, upload as its own session batch, mark each frame with the annotator's null tool - because a folder copied into a set by hand is the route that leaves the frames unmarked and therefore out of the version), `audit_v2.py` (bucket audit vs. §2), `plan_split.py` (three split plans: A strict-by-batch, B stratified per cell, and `--holdout-session sN`, which puts a whole capture session in `test` and is the only one whose test set is a session `train` never saw; it treats a batch as a *(capture session, class, distance)* bucket, prices a session spread across splits, and prints a session × split table with a verdict — with one session the term is constant across every three-split assignment and the applied plan is pinned unchanged by a test — and it names the `(class, distance)` cells each plan leaves with **no train images**, which is a *reported* number rather than an enforced one because a whole-batch plan over a single session cannot satisfy it: pinning those cells into train would leave nothing held out, so constraining the search would silently trade 70/20/10 away for a number it cannot reach. `--holdout-session` is where the constraint *is* enforceable, so it fails closed — exit 2, no plan written — when holding a session out would leave a cell unlearnable), `build_dataset.py` (the local merge: v1's ingested export plus v2's decided, placed frames into one set at `640x640`, stretched — v1's class *indices* remapped by name, test frames that duplicate a train one dropped, polygons reduced to their boxes. For every v2 frame it writes it records the class the frame was *staged as* (`tags`) and the distance it was filed under (per frame in `distances`, and summed per split under `sources.v2.distances`) — counted over the frames that are *in* the set rather than the ones each side handed over, so the sides add up to the `splits` block and the doctor refuses a report whose own arithmetic does not reach the dataset it describes — because the built set holds no manifest and those are the last places the two facts exist — which is what lets `dataset_doctor` check a drawing against its own frame's class, and say which distances the per-distance grid will never be able to measure. It asks the human pass's gate on that same copy first and one door earlier than a run does (`pass_gate`, which is `accept_v2.machine_only_gate` - the *counts* half deliberately, since a build's counts are its own current measurement of the store it just read, where the stamp exists for a later reader, and asking it here would refuse a Roboflow-labelled set that has no provenance by definition - with `--allow-machine-only` as the deliberate override for a set built to be *read*), because a set whose `valid`/`test` hold a machine-only decision is one `train_model` and `accept_v2` both refuse: building it could only replace a usable set with an unusable one, and `--force` is exactly the command that would do the replacing. It runs the doctor on the staging copy before swapping it in, so a merge the doctor would refuse never replaces the previous set, and it refuses a `--v2` that is not a staged set (read through its manifest, a wrong directory contributes zero frames and no error) or a v2 side that would contribute no frame at all; it translates **both** sides' label rows into the declared order by name — v1's through v1's own `data.yaml`, v2's through `annotate.store.CLASS_NAMES`, the annotator's own list — which is what makes the merged order a decision rather than an assumption about what the annotator writes, asks whether a source list *can* be translated at all through one shared rule asked by each side before it writes a frame and by the dry run in the same words (`translation_problem`, with `annotator_class_problem` for the annotator's own list, and only the fatal direction on v1's side, where a class with no v1 frames is a capture gap rather than a translation failure — the relation itself being `generations.class_gaps`, the same owner `train_model.check_export` judges an export with and `clean_v2`'s `sanity` rows judge the live project with, so `[n for n in names if n not in expected]` has one implementation rather than a copy per tool - So `weight_order()` reads each weight's class list from the record `--install` writes beside it and refuses a weight that has none (assuming is what produced the 0.142), and a weight that indexes a reordering is measured on an `order_view()` - a whole set with the same hardlinked frames and the same boxes, only the class column moved, built for every split rather than the measured one because a view that lied about `train` would be a trap for the next `--split`. Each weight's own order also names its detections in the counting pass, since a box's name is `classes[index]`. The two lists must name the same products: they are not a reordering in general, and when they are not, the two lists are printed instead of a number nobody could read), and its crowding claim is cut by distance, for the same reason `--val`'s grid is: a total over the split can rise while `far` gets worse (a `close` frame that gains a second item and a `far` frame that loses one are the same number), so the claim is made on `--claim-distances` (default `mid,far`, `none` for a run that is not making it) and a claimed distance the split files **no frame at** is a failure rather than a pass, since `mid` unmeasured is not `mid` held - the same reading `machine_only_verdict` takes of a report it cannot verify, and the table prints `-` for a row nothing was asked in rather than `0`. The per-distance rows are a regrouping of the *same* two counting passes (`crowd_by_distance`), so a row and the total above it cannot be two measurements, and `--iou-sweep` sweeps each claimed row over its own frames - no more expensive than sweeping the whole split, because the rows partition it - because the count being quoted is a row's and that is the number whose dependence on the threshold needs saying), `dataset_doctor.py` (the gate between the merge and the GPU: six silent failures — a class list in another order, a label row nothing can read, a frame drawn under a class other than the one it was staged as (through `label_classes.tag_mismatch`), a test frame duplicating a train one, a merge report describing a different build (a stale split count, a tag naming a frame the set does not hold, or `sources` whose sides do not add up to it), and a merge whose v2 side contributed nothing — with `--generation auto` resolving which generation's order the labels index, plus the v2 distance mix as a readout and two warnings for the distances that cannot be measured; `train_model.py --yes/--val` and `accept_v2.py` both call `check_and_report`, so a set that fails it is neither trained nor measured, and `build_dataset` gates its own staging copy on the same verdict. `train_model` asks one gate the doctor does not: `pass_gate()` runs `accept_v2.machine_only_verdict` (imported inside the function, since `accept_v2` imports `train_model` for `IMGSZ`) before the doctor, so a locally built set whose `valid`/`test` still hold a machine-only decision is refused with exit 2 *before* the GPU rather than after it - the run is the expensive part and `valid` is the split the run selects on, so a run that skips the pass produces numbers that have to be discarded and a checkpoint chosen against an untrusted signal. Every one of those readers used to replace them - naming `cleaned-v2-s3` silently merged no hard negatives, and the snapshot, the merge and the plan all reported a smaller, perfectly consistent set with nothing to flag, which is the failure mode the list exists for. Replacing them is still reachable, as a decision rather than a side effect of naming a directory: `--no-extras` / `include_defaults=False`). Every tool that scores a weight against labelled frames refuses a set whose labels are not in its generation's class order before it measures anything (`train_model.require_labels_order`, asked by `audit_recall.py`'s `collect` and `label_sizes`, by `spec_check.py`, `clamp_probe.py` and `unsure_probe.py` in their own `main`s, and by `accept_v2` in the form of its own per-weight order evidence): a label row's class column is a **bare position** in the set's declared list, and `check_export` compares names by membership - so two lists holding the same products in different orders pass everything else and every detection is attributed to whichever product sits at that position, with no error anywhere. Measured, `audit_recall.py --generation v2` over v1's export printed `0.000` recall for every class, counted 97 instances of a product that set holds none of, and printed a shooting recommendation on top of it. What the guard deliberately does *not* refuse is a **weight** from another order: `collect` re-keys every detection through the model's own names (`names[int(k)]` → `wanted[name]`) before anything is compared, which is what lets a v1 head be audited against a v2-ordered set correctly (on a 60-frame sample of the merged set's `test` split it reproduced the weight's own recorded per-class numbers, `555 sardines 155grams` at 0.742 against the record's 0.732) - and refusing it would be the cry-wolf guard `check_export`'s own docstring warns about. The asymmetry is the rule: a prediction arrives with the model's names attached and can be re-keyed, a label carries an index and nothing else. And the build refuses to *emit* a set those tools would refuse: `build_dataset.declared_order_problem` reads the declaration it just wrote back off the staging copy before the swap and stops when `names` and the `generation` recorded beside it cannot both be right (the shape `make doctor`'s `auto` default rejects a minute later, and one the build's own doctor run cannot see because that run is handed the generation the build meant), and when the two lists a row can be translated between do not name the same products — the same shared rule asked against the names the artifact carries rather than `CANONICAL_NAMES`, since every row on both sides is a *position* in the list that wrote it (v1's export's, or `annotate.store.CLASS_NAMES`), and `build_v2` remaps v2's by name exactly as `build_v1` always did v1's, so a declared order the annotator does not write in is a translation rather than the silent mislabelling it used to be: a copy verbatim under another declaration filed every v2 row under a neighbour with the doctor and every measuring tool still passing, since all of them read the declaration rather than the rows. Both clauses are constants disagreeing with each other, so the message prints both lists, and the check runs under `--allow-machine-only`/`--allow-unassigned` too - those land a set for *reading*, and the order is a fact about the artifact rather than about how much of the pass has been worked. Their tests live in `sidecar/tests/` — one module per tool (`test_plan_split.py`, `test_clean_v2.py`, `test_generate_version.py`, `test_label_progress.py`, `test_build_dataset.py`, `test_train_model.py` with `test_train_model_val.py` and `test_train_model_distances.py`, `test_generations.py`, `test_audit_recall.py`, `test_spec_check.py`, `test_clamp_probe.py`, `test_capture_hard_negatives.py`), the cross-tool drift guards in `test_dataset_drift_guards.py` and `test_class_order.py` (the class-order rule, and each of its four call sites exercised through its own `main`, so a tool that dropped the check fails there rather than at the next operator's terminal), and the fixtures they share in `tests/dataset_tool_helpers.py` — and run in the normal pytest pass (`pytest.ini` puts `tools` on `pythonpath`), so a class rename that breaks continuity fails the suite instead of silently mislabeling data.

**Added 2026-10-06.** `build_dataset.py --geometry fit` writes each frame at its own shape (long side `--size`) and declares `resize_mode: letterbox` in the set's `data.yaml`; the default `stretch` is unchanged. `train_model.py --install` records that declaration (`read_export_resize_mode`) in place of the generation's default, and `--name <stem>` installs a second weight of one generation beside the first. `build_v1` leaves out v1 frames whose label file is empty (all 17 were unboxed products) and drops a box nested in a larger box of the same product (`drop_nested_rows`). `ab_live.py` records a guided StreamCam clip per product plus an empty basket and runs two weights over the identical frames through the app's own detector and acceptance rules — the comparison the phone-photo test splits cannot make.

Code and data are deliberately separated: the tools are tracked, but everything they produce (staged JPEGs, `manifest.json`, split plans, `upload_state.json`, and the `.env` with `ROBOFLOW_API_KEY`) lives in a gitignored **workspace**, `sidecar/data/datasets/`, relocatable via `SCANNCART_DATASET_ROOT` (`workspace.py` is the single source of that path). Paths inside it are relative to each tool's output directory, so the workspace can be moved wholesale but not in pieces. The workspace also holds `v1-source-zips/` — v1's six raw capture archives, 3.9 GB that used to sit inside `.git` (see `workspace.py`'s docstring); nothing in the runtime or the v2 pipeline reads them.
