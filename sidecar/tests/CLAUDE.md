# Guards, mirrors and doc checks (`sidecar/tests/` and CI)

<!-- Loaded on demand: Claude Code reads a CLAUDE.md the first time it works in this folder. The root CLAUDE.md is the short overview; `/codebase-notes` loads this file by name. -->

Why the checks beyond ordinary unit tests exist, what each one reads, and where each deliberately stops.

## Gates outside `make test`, the Makefile check, and the doc-command checks

`make verify-clamp` and `make verify-unsure` are the two targets that need data the repo does not
carry — an installed weight and the staged negatives, plus a camera for the second — so they are
deliberately *not* part of `make test`, which CI runs on a bare checkout. They fail loudly when the
inputs are absent rather than skipping, since a skip there is a silent pass on the only checks that
say the suppressions still work on real frames and still catch the two phantom families.

What those gates need is the *measurement*, not the claims' wording, and that distinction is a guard:
`test_probe_claims.py` pins the claim tables the three probes declare (`clamp_probe.py`'s five,
`unsure_probe.py`'s nine, `spec_check.py`'s five PRD targets, plus the one row each probe's
ladder-miss branch produces instead of the rest) by reading their source with `ast` — never importing
them, since that would drag numpy, torch and cv2 into the run. It is an equality rather than a subset,
so a claim deleted, added, reworded or reordered fails on a bare checkout, which is otherwise the
hardware gate's job alone and so nobody's on a normal commit; each claim also has to still carry a
literal statement and a reading, because the engine's rule about that is enforced at construction,
which needs the tool to run. The verdict words are re-rendered from the tool's own `Claims(...)` call
and held to the sentence the repo documents — the run sheet's `all 5 PRD targets pass` is checked
against the tool that prints it — and a canary drives the extractor over a synthetic builder, since
the real tables cannot be broken in the suite. The probe's *premise* is pinned too: that
`verify-clamp`/`verify-unsure` are still Makefile targets and that `pytest.ini` does not collect
`sidecar/tools/`, because if one of these measurements ever became a CI step this guard would be a pin
beside a check that already runs and should be folded into it.

`make verify-live-layout` is the third gate and the only one that needs no data at all — a built
renderer and a display. The Live view's premise is preview and rail on one screen with no page
scroll, which is a claim about geometry, and jsdom computes none of it (`scrollHeight` is 0 for
everything), so the suite cannot see it and it was measured by hand until this existed: the target
builds the renderer, draws it in Electron at the canvas and at both corners of the window floor
(`desktop/scripts/check-live-layout.mjs`), and exits nonzero with the per-size table when the page
scrolls. It is out of `make test` for the other reason a check can be, not for missing inputs, and
CI runs it in its own `live-layout` job under `xvfb-run`. The cheap half is in the suite —
`desktop/src/renderer/src/views/liveLayout.test.ts` pins the CSS facts the promise is made of, the
standard the thresholds are stated against, and that the target, this line and that job still exist
— because a measurement wired to nothing is the hand check it replaced.

The Makefile is checked from two sides for the same reason, because nothing else in CI invoked
`make`: a hand edit that merged two `@echo` lines in `help` and de-tabbed two more aborted the whole
file with `missing separator`, which took every target down — `make dev` included — and stayed
invisible to a green suite for a session. A `makefile` job now runs `make help` and dry-runs every
target that index advertises, and the text half is `sidecar/tests/test_makefile.py` in
`sidecar-tests` — the one that still holds where GNU Make is absent, Windows being the case the
README calls optional and the reason it reads the file rather than shelling out.

The one guard family here that reads *data* rather than code is `sidecar/tests/test_roboflow_shapes.py`:
the dataset tools' readers run against bodies **recorded** from the live Roboflow API
(`sidecar/tests/__fixtures__/roboflow/`, re-recorded by `make record-roboflow`, which needs the key and
so is not in CI). It exists because a fake is written by whoever wrote the reader beside it and goes on
agreeing with it after the route moves, which is a blind spot no other check in this suite covers - and
because what it pins is where the code's confidence came from: the project route's class values being
annotation counts rather than positions, and the project having generated no version at all, which is
what makes the next one the second. It runs in the normal suite because it needs no network; only the
recorder does, and its README says what each recording is and what a recording cannot carry.

The commands those targets stand in for are checked as well, because a fenced block is meant to be
pasted: three sidecar test modules read every instruction doc's shell fences over one shared reader
(`sidecar/tests/docs_fences.py`), a rule family apiece so each owns its own rules and canaries.
`sidecar/tests/test_docs_interpreters.py` fails on a bare `python` in command position. The uv path
the setup sections lead with activates nothing, so a bare one is the system interpreter and cannot
import the app at all — and the local inference server is worse, since its venv exists precisely
because the sidecar's cannot import it. Creating that venv
(`python -m venv .venv`) is the one legal bare interpreter, so it is a rule; prose is deliberately
out of scope, because an inline mention is as likely to be a quotation of app copy as an instruction.

`sidecar/tests/test_docs_paths.py` holds the second way a pasted line fails, which nothing else in the
suite can see: the path or target it names is not *there* any more. A tool gets renamed, a Make target is dropped, an
npm script is deleted, and every place the old spelling was written keeps reading as instructions —
the tools' own tests import what exists, the `makefile` job runs the targets `make help` lists, and
`scripts/check_doc_links.py` reads Markdown links, so only a reader pasting the block finds out. So a
line in a shell fence is read as an invocation when it leads with a command word or a path, and then
every path on it is checked against the checkout, a `make` target against the Makefile, an `npm` script
against a `package.json`. The shape that keeps it quiet is the interesting half: a line that leads
with *neither* is a note — a table row, a tree, a diagram — and none of its words are read, which is
what stops a corpus whose fenced lines lead with 155 distinct words from becoming 155 judgements. A
line that leads with a *path* is still ambiguous, since a listing's rows look the same, so that one is
settled by typography rather than vocabulary: this repo aligns a listing's annotations into a column
and draws its diagrams with arrows, while a command is paths and flags on single spaces. Deliberately outside it: trees a fresh
clone does not carry (the venvs, the dataset workspace, `sidecar/models`, `runs/`), values only the
reader knows (`path/to/...`, `<workspace>`, `$HOME`, globs), whether a *tool* is installed (`uv`,
`docker`, `npx`'s binary — a machine fact, not a repo one), and a block's own working directory, which
is why a path is accepted under the repo root, the doc's own directory or `sidecar/`/`desktop/` and a
`cd` argument is not checked at all. The floors and the artifact count it reports are measured numbers
in the module, pinned so a walker that stopped reading fences cannot pass by finding nothing.

`sidecar/tests/test_docs_options.py` holds the third: the names *inside* those commands, judged
against the file that owns the answer. The script a line runs is found (a `.py` at the head, the one
an interpreter is handed, or
`-m <module>` when that module is a file here), and every flag and leading verb on the line is checked
against that script's own `add_argument`/`add_parser` calls — so a dropped `--strict`, or a
`clean_v2.py` verb that was renamed, fails the suite rather than exiting 2 in a reader's shell. The
options are read as *text*, like the Makefile's targets, because those entrypoints import torch,
ultralytics and the app's runtime in their module bodies; the price is stated with it — a parser built
through a shared helper is in the module that defines it, `-h`/`--help` are assumed unless the file
passes `add_help=False`, and a flag that lives on a sibling subparser counts, so the claim is "this
tool knows the option" rather than "this invocation is well-formed". A script that declares nothing
accepts nothing, so the two entrypoints that are started and left alone are named in `NO_OPTIONS` and
a third one appearing fails a canary instead of passing quietly.

## Hand-synced contracts (sidecar ↔ desktop)

The WS message contract (`FrameMessage`/`StatusMessage`/`InferenceMessage`/`Detection`) — and now the settings contract (`SettingsPayload`/allowed models/allowed devices/defaults) — are duplicated by hand between `sidecar/app/schemas.py`+`settings_store.py` (Pydantic/Python) and `desktop/src/renderer/src/lib/api.ts`+`settingsFields.ts`+`settingsDefaults.ts` (TS). There's no shared schema generation, so keep them in sync manually when either protocol changes. That now includes `ALLOWED_BACKENDS`, and `MIN_TRACK_EXPIRY_S_BY_BACKEND` (mirrored as `minTrackExpiryS()`) — the per-backend floor below which a slow round trip can expire a stationary item and log it twice. That now includes `FieldGroup.home`, and the four `camera_*` `FieldMeta` bounds (which mirror `SettingsUpdateRequest`'s `ge`/`le`). That now includes `CameraProfile.measured`/`sweep_version` and `ControlSupport.autofocus`, mirrored by `MeasuredControl` and the matching fields on `CameraProfileResponse` in `api.ts`. That now includes `StatusMessage`'s `class_names`/`class_warnings` pair — the running model's own vocabulary and the sidecar's verdict on it, both rendered as they arrive and neither re-derived here, since the roster has one owner — and the empty list's meaning on both sides (`not known yet`, never `predicts nothing`). That now includes the inference verdict, in two shapes off one body (`InferenceStatusPayload`): `InferenceMessage`, a third message type rather than two more fields on `StatusMessage` — it describes the configured backend, not a capture — whose `state` carries `unknown` for "no server to watch, or nothing asked yet" as *not* a verdict, so the desktop renders nothing for it and a native capture shows no notice at all; and the same payload as `HealthResponse.inference`, which is where the Admin Panel's line gets the address it probed, the failure in the endpoint's own words and the **age** of the reading — a number the pushed copy cannot supply, since the sidecar sends nothing while a verdict stands and the age is recomputed on every read. `null` there means *no server to watch*, which the panel renders as nothing and which is deliberately not the payload's own `unknown`. The resize-mismatch *rule* is also shared rather than mirrored — it lives once in `desktop/src/renderer/src/lib/resizeMode.ts` and is called by both views, since a second copy would be a second answer to the same question. That now includes `UnrecordedResizeMode` (`model`, `resize_mode`, and the split `warning`/`remedy` prose, which two views render and only one can act on) and the `recordResizeMode()` client method, which is how the panel's button reaches `POST /api/models/record`; the mode is read from the sidecar's entry rather than derived in the renderer, and the acknowledgement is read back off the refreshed weights list rather than remembered, so nothing in the panel re-derives either fact. `useActiveWeights` carries that entry as `unrecorded` for the Live view, taken from the same `/api/settings` read as the geometry and the score so the banner and the stats strip cannot describe two different configurations; it also carries the record's own mode as `required` (the evidence, where `unrecorded` is its absence) and the one write that can change either — `record()` with its `recording`/`justRecorded` state — so the two views' buttons are one implementation rather than two. That now includes `ModelsResponse` (stock weights plus `InstalledModel` records — names, the recorded `resize_mode` requirement, `auto_resolves_to`, provenance, `recorded`, `validation`, and `record_facts` (`RecordFact`: `key`/`label`/`value`/`writer`/`detail` — the four facts as one list, each either stated or empty with the writer that fills it in, because the writers are `sidecar/tools/` commands plus the app's own record button and the panel renders the list rather than assembling one): `ValidationRecord`/`ClassRecall`/`DistanceRecall` for what `--val` measured, the last of which is a distance's slice of a split — the same classes over a different image set, `images` being frames where `instances` is boxes, and carrying no `floor` of its own because the block it hangs under already states the one they were judged against, whose `recall: null` means *the split held no instances of it* and must stay distinct from `0.0` all the way to the pixels; labels stay in `settingsFields.ts`, only the *values* travel, so a new model needs no renderer edit. The hook exposes both the names the picker needs and the records the panel needs, deriving one from the other rather than shipping two lists that could disagree), `DetectorProbeResponse`'s `sent_size`/`reported_size` (the remote probe's geometry pair, where `reported_size: null` means the workflow reported nothing and the coordinates were *assumed*, so the panel renders three states rather than a comparison of two numbers), `DatasetStatusResponse`'s fields — including `DatasetTierACell`/`DatasetSessionProgress`/`DatasetBacklogCell` and the `tier_a_*`/`sessions`/`labeling_backlog` blocks the panel renders (the backlog's `background` flag is a field rather than a test on an empty `distance`, because that row differing is a fact about the dataset rather than about a string) — and the one contract the file boundary cannot cover: the snapshot's own shape, which `label_progress.py` writes and `app/dataset_status.py` reads — both tolerate a malformed field rather than raising, because the writer is a separate program. That now includes the two boundaries that are not a schema at all. The one thing the guards watch that is *not* a mirror any more is the annotator's labels directory: it was five spellings of `annotations-v2` (both of the annotator's entrypoints and its store, plus `label_progress`, `import_labels` and `build_dataset`) and it now lives once in `workspace.ANNOTATIONS_DIRNAME`, which every one of them imports - so the guard is a scan for a second spelling rather than a comparison, and it found the `build_dataset` one when it was written. And the **process boundary**, which is a contract of strings rather than of types: the `SIDECAR_PORT=` handshake line, `SIDECAR_PARENT_PID`, the `sidecar:port` channel across main/preload/renderer, and the venv and `run.py` paths `desktop/src/main` resolves and the Makefile launches. Both are pinned - `tests/test_annotate_store.py` (which also asserts the pseudo-class slugs are the tools' own set by import) and `tests/test_desktop_contracts.py` - and both directions, because a rename on one side leaves a sidecar streaming happily beside an app that never learned its port.

## Mirror guards and wording contracts

Context: `desktop/src/renderer/src/lib/settingsFields.ts` / `lib/settingsDefaults.ts` are client-side mirrors of the sidecar's `ALLOWED_MODELS`/`ALLOWED_DEVICES` and `Settings` defaults. The hand-keeping is *checked*, in both directions, by four guards in `sidecar/tests/test_settings.py` that parse these two files — the defaults field-by-field, and the model list, resize modes, devices and backend sets as vocabularies — because nothing on the desktop side can import the sidecar to compare. Each is marked `mirror`, and the marker is the convention now: `sidecar-tests` runs the whole subset as a named step, and a separate `Two-toolchain mirrors` job runs the two whose dependency is pytest plus `pydantic` (module paths rather than `-m mirror` over the directory, because pytest imports every module it collects before it applies a marker) - the rest import the runtime they check: `app/dataset_status` brings in the whole app, and the annotator's guards reach `label_progress` → `clean_v2` → pillow and numpy. A drift failure therefore names the pair it broke rather than a line in a 1,300-test run. Where each guard deliberately stops: prose is not pinned (`MODEL_LABELS`/`MODEL_SPEC_HINTS` wording, hint text) — only the one number in a label a reader cannot check by hand, its class count against that generation's roster. `sidecar/tests/test_desktop_contracts.py` holds the rest of the pair-readers, every one marked `mirror`: the WS/REST shapes in `ws.ts`/`api.ts`, the fixture roster in `src/test/fakes.ts`, `EXPERIMENTAL_MODELS`, the per-backend expiry floor, the two-way field list (`SETTINGS_FIELDS` keys ≡ `Settings` ≡ `SettingsPayload`), every numeric bound against `SettingsUpdateRequest`'s `ge`/`le` (which are `settings_store`'s own constants, so the probe's ranges are no longer a third copy - what is left is a scan that fails if `camera_caps.py` declares a range of its own again, read as text because that module imports `cv2`), and the process boundary — the `SIDECAR_PORT=` line, `SIDECAR_PARENT_PID`, the IPC channels (read as a *set*, so a newly added one that nothing invokes fails here rather than being silently uncovered by a single-match search), and the venv/`run.py` paths the desktop and the Makefile both name. The last reader is the one that pins **wording** rather than shapes, and it sets the convention for any guard like it: `NULL_CONTROL_SURFACES` lists every surface that *describes* what a null camera control means — `camera.py::_undo_for` owns the answer; `settings.py`, `settings_store.py`, `schemas.py`, `test_live_settings.py` and `CLAUDE.md` carry it in comments; `api.ts`, `CameraTuning.tsx`/`.css`/`.test.tsx` and `settingsFields.ts`'s rendered field hints carry it on the desktop, the hints being the one surface an operator reads without an editor, where the wording *is* the explanation rather than a note beside the code — and the guard asserts each surface still carries its load-bearing fragments, matched fragment-wise so a surface may be reworded freely but may not lose the fact. The retired sentence — the one promising the camera would be left alone, which it cannot be, so its return is the regression rather than a leftover — is asserted absent on those same surfaces only, because it is a judgement about this app's own copy, not about every sentence in the repo. That sentence cannot even be quoted here: this file is one of the scanned surfaces, the match is substring-exact, and a future editor rewording around this paragraph should keep it that way rather than "fixing" the dodge. Fragments are matched over a normalizer that drops comment-marker tokens whole: TS/CSS comment markers land mid-sentence across wrapped lines, and `http://` has to survive. The convention is the same-edit rule the failure message states — a null-control surface that is added, moved, renamed or reworded takes its row with it in the same edit, because the fragments live in comments and rendered copy that nothing compiles, so the table is the only place the drift can be caught — and a canary asserts both halves of the guard can still fire, so a normalizer edit that made it vacuous fails instead of passing green. Both guards now run on one engine, `sidecar/tests/wording.py`: a guard is a `WordingContract` table — `name`, `owner`, the two failure sentences, the surfaces, the canary — plus three one-line tests, so the next wording contract needs no copy of the plumbing. The engine validates its tables at construction (an empty surface, a blank fragment, a canary fragment that is not a surface fragment, a retired phrase without its why, a phrase both required and forbidden — each fails loudly instead of pinning nothing), and its canary asserts exactly the pinned fragments, tolerating an extra match only when it is a substring of a pinned fragment: the same sentence in a shorter form, which surfaces routinely carry, is not fixture drift. The convention's second application is `ROSTER_FINDING_CONTRACT`, which pins the sentences every surface uses to describe `class_list_problems`' three findings — the distance-split head that logs one product under three labels, names outside the roster, and the quiet missing-class direction ("Nothing it *does* predict is wrong") — from the owner's own sentences through the models/schemas/main comments (including the one explaining why the roster is *not* mirrored into TypeScript) to the desktop copy that renders them verbatim and LiveView's `classes · roster ok` chip. It has no retired phrase, because nothing about the findings was ever reworded away — a guard without a history does not invent one — and its canary places the comment marker *inside* the pinned fragment's span: a marker at the fixture's edges is dropped with nothing between it and the words, so a broken normalizer survives it and the canary stops proving anything while staying green. The third, `RESIZE_REMEDY_CONTRACT`, pins the assumed-geometry remedy's sentences (`resize_guess`'s two-sentence split, the record route, the merge-not-replace writer, both views' render rationales) and was written table-only against this engine — thirteen surfaces in one table, no plumbing — with its inventory immediately catching a stale sentence in this very paragraph: the dataclass has carried `remedy` since the Live view needed it, and the prose still said two fields. That catch in the guard's first run is the extraction working as designed. Its rows now include the **two doors into one record** — `train_model.py`'s `print_provenance_note`, which reports the `source` an install could not fill, and `resizeMode.ts`'s shared confirmation, which reports the same empty field when the panel's button writes the geometry — plus `models/README.md`, where the two standing in agreement is stated for a reader. Because a rewrite could keep every pinned fragment in every row and still send the two doors to different tools, that claim is not a test of its own at all: it is a **row in the agreement table**, and so is any future claim that several surfaces must agree. `tests/wording.py`'s `AgreementContract` names the tokens the surfaces are agreeing *about* (`--version`, `backfill_provenance.py`, the source index), the span each one keeps its copy in - read by the anchors the file already writes, *both* of them required, so a renamed definition fails loudly instead of quietly widening the search to the whole file (converting that row is what caught `recordedConfirmation` being the last export in `resizeMode.ts`, where the old hand-rolled reader had been falling back to reading the file to its end) - and a canary of those same spans as text. `sidecar/tests/test_desktop_contracts.py`'s `AGREEMENTS` holds two rows today and two parametrized tests walk it: the claim, and a canary that drops each token from each surface in turn and requires exactly that surface and token to be reported, which is what makes every token load-bearing rather than decorative. A second row is the one claim whose surfaces are code rather than prose (`minTrackExpiryS` has to read the floors by the names `settings_store.py` declares them under, since a literal in its body is a second floor the value comparison cannot see). The engine validates a row at construction - fewer than two surfaces (with one there is nothing to disagree with, and the claim belongs in a `WordingContract`), no tokens, a token that is part of another, two spans sharing a name, a canary that does not speak for every span - each fails loudly rather than pinning nothing, so the next agreement is a row and no new test. Those rules have a test module of their own, `sidecar/tests/test_wording_engine.py`, because every property that makes a claim worth having is a negative one - a row that pins nothing, a span that quietly reads the whole file, a canary that proves the check ran rather than that it works - and none of them show up in a green run of the claims. `sidecar/tests/desktop_mirrors.py` is where the shape reading lives (TS literals, interfaces, arrays of object literals); the wording contracts read their surfaces as whole files instead — `tests/wording.py` reads and never imports them, because several surfaces (`.ts`, `.css`, `CLAUDE.md`) have no Python import to offer — because their claims are prose, not literals. `sidecar/tests/test_docs_claims.py` is the same idea pointed at prose, and is marked `docs` rather than `mirror` because a doc is not a second toolchain: it reads `CLAUDE.md`, `docs/RUN_SHEET.md`, `docs/MODEL_TRAINING.md` and the run-desktop skill (the fourth because it states the same §12 fixture the other two point at, and carried the same stale class count) and checks the five kinds of sentence that are really a copy of a code fact - a class count, a settings default, a floor or ratio, a split or artifact name, and the size of one of the contract tables below - the surfaces in it, or how many rows it has - read from the table itself (`thirteen surfaces in one table` is `RESIZE_REMEDY_CONTRACT`'s row count, so adding a row to that table fails here rather than leaving the sentence reading true; and a count whose sentence names no such table fails too, since a number that names nothing is the shape this module exists to catch). Everything it cannot check is deliberately left alone: the live dataset counts the run sheet also carries move with the data, and pinning those would fail on a labeling session, which is how a guard stops being read. Its exemptions sit in one place at the foot of the file, keyed by the phrase with the reason it is allowed, the docs it was written about and the one *claim shape* it is excused from - an arm plus the pattern that matched, since this arm has several, which is what stops a phrase written for the count shape from silencing the subset or the roster-pair one. Those arms are declared with the test that runs them and the patterns they scan with, which a check reads off that test's own body (one level into the helpers it calls) and holds to the same set the call sites ask with. The row and the rule that keeps it live are `tests/exemptions.py`'s, shared with the two other guards that keep such a table (`test_class_order`'s sites in the tools tree, `test_docs_interpreters`' pasted commands) so that a phrase, its reason, its shape and its liveness check are one shape rather than three copies; what each guard supplies is its own shape names and its own reader, that reader being the one thing that genuinely differs (a doc's text, or the sites one path's scan rendered). Each row is asserted still present, still excusing a claim its own shape flags, and excusing it for that shape alone, so an exemption cannot outlive the sentence it was written for, cover whatever replaced it, or make another shape skip text it was never written about; and a table with no rows has to declare itself empty (`designed_empty=True`), because an empty table is the one failure that rule cannot see from the inside - it has nothing to check, so a cleared table would pass it in silence - and that declaration is dropped in the same edit as the first row. A scan that skips something collects a `Waiver` for it - what was let through, where, under which shape and for which reason - so each guard's own test states the rows it applied (a row that is live but which the scan never reaches is a waiver nobody is using) and the failure report quotes them through `waived_note`, which is how a reader sees what else was touched rather than having to know the table. Where a doc number *is* the code's number, prose is the wrong place to keep it at all, which is what `sidecar/tools/docs_sync.py` and `make docs-sync` are for: it owns the sentences whose value the code determines - a class count, a settings default, the recall floor, the split ratio, the crowding margin, the augmentation table the trainer prints, and the reload word in the tuning table (the site this tool found first was `conf_threshold`, documented as `Restart-required.` while `settings_store.HOT_RELOADABLE_FIELDS` has said otherwise since `set_conf()` existed) - and rewrites each from its owner. The two are complements: the sync renders what it can anchor, and the guard catches what it cannot (a class count in ordinary prose, a measured recall, a script's own `PASS` count). `test_docs_sync.py` mutates every site's span and deletes every site's sentence, so the one failure mode that matters - a site that matches nothing, rewrites nothing, and reports success - cannot pass. It is what corrected this round's stale counts: every prose class count in these four docs now has to be a number the roster and the distance axis can produce (a product-and-distance head, never a number from the era before the dropped class), `RUN_SHEET.md` §12's expectations describe a scratch fixture sized by `generations.V2.classes` x `DISTANCE_ORDER` rather than by a product list written into the driver - a hard-coded one is exactly why that section's numbers outlived the class they included - and `MODEL_TRAINING.md`'s capture guidance now quotes the defaults `settings.py` actually has, not the 1280x720@60 geometry it used to name. `test_docs_claims.py` pins the fixture's shape too, because a doc describing something nothing builds is how a stale number survives a dataset change. It also reports a contract table that no doc and no check names - declared, validated at construction, and reachable by nothing - since a table nothing reaches for reads as maintained while nothing can fail on it. Its findings are reported through `tools/claims.py` like every other claim this repo decides: an arm appends a `(where, why)` pair - what is claimed and the reading that came out wrong - and the failure is one claim table, with the verdict naming the failing claims, a row each, and the owner of the fact plus the remedy on the last line.

`sidecar/tests/test_stated_counts.py` is the same family pointed at a claim the *text* owns rather than the code: a sentence that states a count and enumerates the items under it (`Four states have no answer here:` over five of them, `Five things make this not a re-run:` over four). Nothing outside the file can answer that, which is why it survived - each half reads as true on its own, and the reader who would have counted them is the reader the sentence was written for. It is marked `docs` and reads the two corpora the shape was found in, `sidecar/tools/*.py` and `docs/*.md`, because a tool's docstring is prose a reader reads. It counts the items of the two shapes these files write them in - a `**Heading.**` paragraph, or a bullet/ordered list, one list being one marker style - and checks the number against that count. A claim whose items are not a list is not skipped: it has to be a row in the module's own table, with the reason its items cannot be counted, which is the one edit a new `Three reasons:` written in prose costs. The two judgements are separate shapes, so a row written for prose cannot silence a list whose length disagrees with its number, and the arm reports both the count it read and the claims it read it from - through `tools/claims.py`, the same engine the three measured tools report through, so its failure is a claim table in the one shape the repo uses and the score it states is `M of 37 claims FAIL` rather than a count of only the findings.

`sidecar/tools/claims.py` is the one place a claim is declared, verified and reported, and it exists because five surfaces decided claims while four of them carried their own answer: `clamp_probe.py` and `unsure_probe.py` were the same `Check`/`verdict`/`strict_failed` block twice over - differing only in a hand-tuned pad width, 52 against 56 - `spec_check.py` was a third spelling of the same idea for its PRD targets, and the two text guards above assembled their failures as prose at each call site. A claim is now `Claim(statement, reading, holds)`: what is claimed, the reading that decided it, and the answer, with both strings required, because a verdict with no evidence behind it is the shape this engine exists to make impossible. `Claims` is the table it lives in - the noun and the two verbs its verdict counts in, the rows, how many claims were decided, and the remedy - and it owns every part of the report: `verdict()` is the single sentence (`all 5 claims hold`, `1 of 9 claims FAIL: <the failing statements>`, `all 5 PRD targets pass`), `block()` is the section a tool prints, `failure()` is what a test raises, and `exit_code(strict)` is the rule behind every `--strict` run, so the flag is the caller's and the answer is the table's. The wording stays each table's own because two of those sentences are *documented output* - `docs/RUN_SHEET.md` states `all 5 PRD targets pass` and `docs/MODEL_TRAINING.md` pastes a `spec_check` row verbatim - which is also why a table whose reading has columns may supply its own `row` renderer. A *scan* reports through `findings(name, owner, rows, read)`: `(where, why)` pairs plus the number of claims it decided, so a guard's failure reads `2 of 37 claims FAIL` in the same words a measured run's does, and the table is built only when there is something to report, which is what makes the engine's refusal of an empty table the failure a broken pattern deserves. Every table validates itself at construction - no rows at all, one statement listed twice so the second reading is never looked at, more failures than claims decided, a blank word in the verdict - because every way of writing a table that verifies nothing is a way of writing one that passes. Its own tests are `sidecar/tests/test_claims_engine.py`, and the last two of them are what keep the unification from decaying: no tool may define its own `verdict`/`strict_failed` or spell the verdict's sentence itself (read with `ast`, so a docstring explaining the idea is not a second copy), and every surface that decides claims has to import the engine.

## Machine state the suite must not touch

`tests/conftest.py` holds one autouse fixture, and it exists because of one file. The source index (`app/source_index.py`, `sidecar/data/source_index.json`) is *machine* state — a record of the runs this machine has trained, beside the settings and the detection log — and it is keyed by a weight's **bytes** rather than by a path, while every fake weight in this tree is built from the same handful of bytes (`b"weights"`). A suite that wrote the real index would therefore have one test answering another's question: an install test adding an entry is enough to make `test_backfill_provenance.py`'s "a weight no run produced is left empty" pass or fail depending on test order. That is not hypothetical — it happened while the feature was written, which is why the guard is suite-wide rather than in the tests that noticed. It redirects the file through `SCANNCART_SOURCE_INDEX`, the same override an operator uses to relocate it, so what the tests exercise is the shipped mechanism; a test that wants a populated index writes one through `source_index.record_source` at `source_index.index_path()`. The rule generalises: anything the app or the tools keep per *machine* rather than per checkout belongs behind an override the suite sets, not in a `data/` file every test shares.
