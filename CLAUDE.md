# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SCANnCART is a capstone prototype for grocery stores: a Logitech StreamCam feeds a Python sidecar that runs YOLO11 (Ultralytics) object tracking, and an Electron + React desktop app displays the live annotated feed and a session item log. Everything runs locally on one PC — no server, no cloud, no network dependency.

Detection sits behind a swappable backend (`detector_backend`): `native` runs the weights in-process and is the only one that satisfies the offline promise; `local_api` and `cloud_api` call a Roboflow Workflow over HTTP. See `docs/DETECTOR_BACKENDS.md` — including §7a for running `local_api` with no Docker. See `docs/PRD.md` for the full product spec and `docs/DEPLOYMENT.md` for out-of-scope future work (edge hardware, cloud sync, etc). `docs/RUN_SHEET.md` is the operational chain — shoot → clean/upload → generate → train → `--val` → install — as the order to run it in with the number each step has to report before the next is worth running; `docs/MODEL_TRAINING.md` is the reasoning behind it and `docs/CAPTURE_CHECKLIST.md` is what to shoot.

Two independent toolchains live side by side and talk over localhost HTTP/WebSocket:

```
Logitech StreamCam ──USB──▶ sidecar/ (Python/FastAPI)  ──ws://127.0.0.1:<port>──▶ desktop/ (Electron/React)
                             OpenCV capture → YOLO11 track            live preview + overlay + item log
                             SQLite detection log                     REST for start/stop/health/logs
```

`desktop/src/main` spawns `sidecar/run.py` as a child process on app startup and shuts it down on quit; the renderer never launches the sidecar itself, it just discovers the port over IPC and talks to it directly.

## Commands

A root `Makefile` wraps both toolchains (requires GNU Make — on Windows use Git Bash/WSL, or `winget install GnuWin32.Make`). Run `make help` to list targets. Key ones:

```bash
make install              # desktop npm install + sidecar venv setup
make dev                  # electron-vite dev (spawns the sidecar) — needs `make sidecar-setup` first
make test                 # desktop vitest + sidecar pytest
make build                # typecheck + electron-vite build
make lint                 # eslint --cache on desktop
```

### Sidecar (Python, in `sidecar/`)

```bash
cd sidecar
uv venv --python 3.12 .venv && uv pip install --python .venv/Scripts/python.exe -r requirements.txt  # or plain venv/pip, see README.md
python run.py                          # prints SIDECAR_PORT=<n>; picks a free port if 8765 is taken
python -m pytest -v                    # full suite — runs entirely against fakes (no camera, GPU, network, or API key)
python -m pytest tests/test_pipeline.py -v            # single file
python -m pytest tests/test_pipeline.py::test_name -v # single test
```

On first capture start, Ultralytics auto-downloads `yolo11n.pt` if not already present. It lands in
`sidecar/` — the process cwd, because a bare `active_model` name (what `presets.py` writes) is
resolved **by name** — not in `sidecar/models/`, which the Model picker reads. Those stock weights
are runtime artifacts, gitignored by `*.pt` and kept on disk so the offline promise does not depend
on the download; do not "tidy" them into `models/`, where the picker would list each one twice and
the built-in entry would resolve to a download instead of the local file.

### Desktop (Electron + React + TypeScript, in `desktop/`)

```bash
cd desktop
npm run dev                # electron-vite dev, full app (needs sidecar venv set up first)
npm test                   # vitest run (headless; sidecar is always faked)
npm run test:watch
npx vitest run src/renderer/src/hooks/useSidecarStream.test.tsx   # single file

npm run lint                # eslint --cache
npm run build               # typecheck + electron-vite build
npm run build:win / :mac / :linux   # package with electron-builder
```

## Architecture

### Sidecar (`sidecar/app/`)

- **`main.py`** — `build_app(state_factory)` builds the FastAPI app. All sidecar state (settings, active pipeline, WS clients, logging store, current session) lives in a single `AppState` dataclass instance closed over by the route handlers — there's no global state. Routes: `GET /api/health`, `GET`/`PATCH /api/settings`, `GET /api/system-info`, `GET /api/presets`, `POST /api/settings/preset`, `GET /api/cameras`, `GET /api/models`, `POST /api/models/record`, `POST /api/detector/probe`, `POST /api/capture/start`, `POST /api/capture/stop`, `GET /api/logs`, `GET /api/dataset/status`, `WS /ws/stream`. `source_factory`/`detector_factory` on `AppState` are the injection points tests use to swap in fakes. `POST /api/detector/probe` builds the detector through that same factory and, for the remote backends, sends a frame **shaped like the capture** rather than a 64×64 square — an aspect mismatch cannot show up on a square — then reports the `sent_size`/`reported_size` pair the detector recorded (read with `getattr`, because that record is a remote-detector extra rather than part of the `Detector` protocol, and the native path leaves both null: its geometry is a settings fact, not something a call discovers). **`WS /ws/stream` sends the current capture state as its first message on connect**, before anything streams: until that existed the only status messages a client ever received were its own start/stop responses and pipeline errors, so a renderer joining an already-running capture (a reload, a second window) showed `idle` over live frames and skipped its `/api/logs` recovery, which is gated on `running`. Three consequences worth knowing: any client's first message is now a `status`, not a frame (sidecar tests use `tests.next_frame()` to skip it); the renderer seeds that recovery from the handshake *or* from `onOpen` — the state usually arrives after the socket opens, so `useSidecarStream` needs both, latched to one `/api/logs` call per connection; and the handshake carries a **`detail`**, because `state` alone cannot describe a capture that *died* before this client arrived — teardown leaves `idle`, which is exactly what a capture that was never started looks like, so `AppState.last_error` stores the pipeline's own sentence (`"Capture stopped: …"`) on the way out and the snapshot sends it. The handshake carries **`class_names`/`class_warnings`** for the same reason: `Pipeline` hands the model's class names up once, `_on_class_list` stores them, judges them (`app/roster.py`) and broadcasts the pair, and a client joining an already-running capture is therefore told the model predicts 24 classes instead of having to infer it from the labels going past. It broadcasts **unconditionally**, which reversed an earlier rule ("a clean list is not news"): the names are also a readout — the Live view's stats strip shows how many classes the running model has — so staying silent on a healthy capture would leave that chip absent on exactly the models that are fine. Both fields are cleared with the rest of the runtime in `_teardown_capture`, since neither describes anything once nothing is loaded. It is cleared *before* `state.pipeline.start()`, not after: the error handler runs on that thread, so a detector that fails on its first frame can record its reason before the next lines run (and an `_acquire` failure raises before that point, leaving the stored reason alone). Settings patches are always applied via `_apply_settings_patch()`, which `setattr`s onto the existing `Settings` instance (never replaces it — `Pipeline` holds it by reference) and rejects (`409`) changes to `RESTART_REQUIRED_FIELDS` while capture is running.

  Capture lifecycle has five invariants worth knowing before touching it. **Acquisition runs in a threadpool** — `source.open()` blocks for ~37 s on a StreamCam, and inline it froze the event loop so `/api/health` and the WS handshake stopped answering. **The detector and the camera are built concurrently** — the detector factory is submitted to a worker before `source.open()`, so the ultralytics import overlaps the device open instead of stacking after it. Because they overlap, either can fail while the other is still building, so `_acquire` resolves both before returning anything and releases whichever one succeeded; abandoning the future would strand a fully loaded model (VRAM on CUDA) on every failed start. **Teardown goes through `_teardown_capture()`**, which claims and clears the pipeline/source/detector/session under `state.teardown_lock` in one step, because the HTTP stop handler and the pipeline thread's own error handler race here; the thread join happens *outside* the lock, since the error handler runs on the pipeline thread and holding it across a join would deadlock (that path passes `join_thread=False`). **Start reports `running` as soon as the pipeline thread is up** — no first frame is awaited, so a camera that opened but never delivers reads as a successful start for the ~3 s it takes `CameraCapture` to declare the device dead, at which point the WS `error` status carries the explanation. **Frame sources expose `release()`, not `close()`** — detectors are the ones with `close()`; `_release()` handles both.
- **`camera.py`** — `CameraCapture` owns an OpenCV `VideoCapture` and runs a background thread writing into a `LatestFrameBuffer` (a lock-guarded size-1 slot: newest frame always wins, no queue buildup/backpressure). `FakeFrameSource` is the test double. `set_controls()` queues control changes for the capture thread rather than writing them inline: `cv2.VideoCapture` is not thread-safe and `_loop` is calling `read()`, so a `set()` from the FastAPI request thread would race it. Changes are coalesced into a dict, so a fast slider drag costs one write. A device that refuses a value sets `control_error` and keeps streaming — `_loop` has no handler above it, so letting the write raise would kill the capture thread with `failure` unset, freezing the feed with nothing to explain it. `_default_capture` pins `cv2.CAP_MSMF` on Windows deliberately (the StreamCam delivers 60 fps at 1080p over MSMF versus ~15 fps over DirectShow) and drops to OpenCV's auto backend only when MSMF can't open the device at all — so don't "helpfully" switch a misbehaving camera to DSHOW. `_loop` gives a stalled read `FAILURE_TIMEOUT_S` (3 s) as a deadline rather than a retry count, so how long a user stares at a frozen preview doesn't depend on the backoff, then sets `failure` and stops the thread; `Pipeline.process_once` raises that and `main.py`'s `on_error` reports it as an `error` status before tearing capture down. `open()` returning True is **not** evidence of a working camera: the MSMF wedge opens cleanly and then never delivers a frame (symptoms and recovery in the `run-desktop` skill), so nothing should gate on `isOpened()`.
- **`camera_caps.py`** — measures what a camera can actually do, and now what values to set. Nothing here trusts `cap.get()`: on this hardware, setting `CAP_PROP_EXPOSURE` moved delivered framerate from 12.3 to 30.3 fps while the getter kept returning the old value, so a control counts as supported only when the image or the frame rate visibly changes. `probe_controls()` is destructive by design — it leaves the device holding whatever value it wrote rather than reading a value back through the same lying getter to "restore" it — so `calibrate()` reopens the device before using it further. `calibrate()` then runs `probe_controls` (which controls the device honours) and `sweep_controls` (what to set them to) in a fixed order: autofocus off, exposure onto `BRIGHTNESS_TARGET`, focus for the sharpness peak, brightness to trim the remainder. Order is a dependency — a focus value written under a live autofocus is hunted away from, and sharpness is unmeasurable on a frame that is blown out or black. `exposure_ceiling()` computes the longest exposure that still clears the fps floor arithmetically, rather than discovering that cliff by walking the search off it. `CameraProfile.measured` records the evidence (value, metric, baseline, reached) separately from `recommended`, which is policy — that split is what keeps `camera_derive` pure and re-runnable against a stored profile. `ControlSupport.autofocus` is measured the same way (`probe_autofocus`, watching whether a pinned focus value holds under `CAP_PROP_AUTOFOCUS=0`) rather than inferred from other controls working. `sweep_version` is 0 for profiles written before the sweep existed. An empty `recommended` with `sweep_version: 0` means "never measured" (recalibrate to find out); the same empty `recommended` with `sweep_version: 1` means "measured, and this camera answered nothing" (recalibrating won't help) — opposite operator actions the field exists to distinguish, since neither state can be inferred from the other.
- **`camera_search.py`** — `search_to_target` (binary, for a monotone curve) and `search_for_peak` (ternary, for a unimodal one). Pure and device-free: `probe` is a callable the caller supplies, so the algorithms are tested against synthetic response curves rather than a camera. Two algorithms because the two curves differ — brightness rises monotonically with exposure, while sharpness peaks at the subject's distance. `SearchResult.span` is the flat-curve detector: a sharpness sweep that moves nothing means nothing was in frame, which is reported rather than resolved into a confident wrong answer.
- **`camera_derive.py`** — turns a `CameraProfile` into a settings patch, pure and total so it can be tested against hand-written profiles and re-run against a stored one. Prefers `profile.measured[k]` — a real observation — and falls back to the old flat-boost constants only for controls no sweep ever measured (an un-swept profile, or one the device ignored). `camera_autofocus` is proposed only when `controls.autofocus` measured true, and `camera_focus` is withheld entirely when it's false, since a lens that won't hold a lock just wanders off whatever value is written.
- **`inference.py`** — `YoloDetector` wraps `ultralytics.YOLO(...).track(..., persist=True)` for detection + multi-object tracking (stable `track_id`s across frames) and normalizes results to 0–1-relative boxes via `normalize_detections`. `RoboflowRemoteDetector` satisfies the same `Detector` protocol over HTTP: it downscales before transmit, filters by confidence client-side (the workflow declares no parameters), normalizes against the image size the server echoes back, and assigns track ids locally *only* to detections the response didn't already track. It also keeps `last_geometry`, a frozen `RemoteGeometry(sent, reported)` recorded on **every** call (set before the no-predictions return, or a probe — which always sends a blank frame — would never populate it): `sent` is what `_encode` transmitted and `reported` is the response's `image` block, with `None` meaning the response carried none at all. That third state is why it is a record rather than a number: with no block the detector *assumes* the coordinates are relative to what it sent, and `POST /api/detector/probe` reports both so an operator can catch a workflow that re-frames the image before the model sees it — the remote analogue of `resize_mode_resolved`, and the only geometry fact available when the weights live inside someone else's workflow. The downscale keeps the aspect ratio deliberately: a uniform scale commutes with whatever the model does next, so `remote_infer_size` decides detail rather than object scale, and a non-uniform one would warp objects before they left the machine.
- **`pipeline.py`** — `Pipeline` runs its own thread (`process_once` in a loop) that: pulls the latest frame, optionally skips frames (`infer_frame_skip`), runs inference, drops detections whose class is not on the hot-reloaded `class_allowlist` (empty = keep everything), JPEG-encodes a preview (`render_preview`, which returns the JPEG and its boxes together, resized to `preview_height`), logs detections, and pushes a `FrameMessage` via the injected `on_message` callback. Track lifecycle (`entered_at`/`left_at`) is derived here: a track not seen for `track_expiry_s` is considered "left" and resolved in the log; `resolve_open_tracks()` force-closes everything still open on capture stop. The preview mirror lives here too, in the preview path only (`preview_mirror`, default on): capture, inference, the logging store and dataset frames keep the true orientation, because these weights were trained on ordinary photographs and a mirrored input asks them to read reversed text and mirrored brand marks. `render_preview` reflects the image and the boxes together behind one call so the two cannot disagree, and both emit paths go through it — reflecting in only one would flicker the overlay at the inference rate. `infer_frame_skip`, `preview_height`, `preview_mirror`, `track_expiry_s`, and `class_allowlist` are all read fresh from `self._settings` every call, so mutating them in place on a running pipeline takes effect immediately (no restart) — everything else (`active_model`, `device`, camera params, `conf_threshold`) is baked into `source`/`detector` at construction and needs a stop/start cycle. `_report_class_list()` calls `on_class_list` **once**, with the detector's class names, on the first inference that knows them — not at construction, because `YoloDetector.names` is deliberately empty until then (filling it eagerly would build a second ONNX session) and a check there would call a perfectly good weight one that predicts none of the roster.
- **`dataset_status.py`** — reads the labeling-progress snapshot the dataset tooling writes (`sidecar/tools/label_progress.py` → `sidecar/data/datasets/cleaned-v2/label_progress.json`) and hands it to `GET /api/dataset/status`. Deliberately file-only: the sidecar makes no Roboflow call and needs no key, so the app keeps its offline promise and the roster travels *inside* the snapshot rather than as a second copy here. `available: false` is a 200, not a 404 — "nobody has run the tool yet" is the state the panel starts in — and `generated_at`/`age_seconds` ride along because the numbers are only as new as the last tool run. It keeps its own copy of the workspace path on purpose (a packaged sidecar does not ship `sidecar/tools/`), which `tests/test_dataset_status.py` pins against `tools/workspace.py`. The snapshot also carries Tier A's **capture gap** (`tier_a_*`), sourced by `label_progress.py` from `clean_v2.TIER_A_CELLS` so the panel and the folder skeleton cannot disagree; an older snapshot without the block reads as "no gap" rather than erroring, and `tests/test_dataset_tools.py` pins that the progress tool imports that table rather than copying it. It carries the **capture-session spread** (`sessions`) for the same reason: `label_progress.py` reads the session off each image's tags — not the manifest, which the hard negatives are absent from — and `splits` is *derived* here from the three counts rather than trusted from the file, so the flag the panel colours on cannot disagree with the numbers printed beside it. The panel marks a session only when it sits in both `train` and `test`, which is narrower than the `splits` count on purpose: a session spread across train and valid is the ordinary remainder and does not spoil a test number. It also **derives the labeling worklist** (`labeling_backlog`: the same counts as `classes`, ordered most-remaining-first with finished cells dropped) rather than having the tool write a second list, since `by_cell` already carries every number that needs and a second list in the file could only disagree with the first. A cell is one class at one distance, which is what makes the list actionable in a way a per-class table is not: the thing that stalls a project is a distance bucket nobody opened, not a class nobody started. Two details are load-bearing — `remaining` is `total - decided` computed on read (clamped at 0, so a snapshot claiming more decided than total cannot sort first with a negative), and the hard-negative pseudo-class is appended from `by_class` because its frames carry no distance and so have no cell to sit in, which would be the one omission with a cost (its frames are marked with the annotator's null tool, and an unmarked one never enters a version).
- **`logging_store.py`** — `LoggingStore` is the sole SQLite writer (one connection, one `threading.Lock`, since the FastAPI request thread and the pipeline thread both touch it). Schema: `sessions` (one row per start/stop capture cycle) and `detection_events` (one row per track per session, `max_conf` tracked across the track's lifetime, `left_at` NULL while still in frame).
- **`schemas.py`** — Pydantic models shared by the WS frame protocol and REST responses (`Detection`, `FrameMessage`, `StatusMessage`, `HealthResponse`, `LogEvent`, `LogsResponse`, `SettingsResponse`, `SettingsUpdateRequest`, `SystemInfoResponse`, `PresetsResponse`, `DetectorProbeResponse`, `CameraInfo`/`CamerasResponse`).
- **`settings.py`** — plain dataclass `Settings` with hardcoded defaults (no env/file loading — stays pure so its own tests never depend on disk state); `resolve_device("auto")` picks `cuda` if torch reports it available, else `cpu`.
- **`settings_store.py`** — `load_settings()`/`save_settings()` persist `Settings` to `data/settings.json` (atomic write via temp file + `os.replace`; a missing/corrupt file or a bad individual field falls back to defaults rather than crashing startup). Also owns `HOT_RELOADABLE_FIELDS`/`RESTART_REQUIRED_FIELDS` (the single source of truth for which settings a running pipeline picks up live) and `compute_warnings()` (soft warnings surfaced in `SettingsResponse`, e.g. an uncommon capture resolution or a frame-skip/track-expiry mismatch). One of those warnings reads the same `resize_requirement`: a recorded `stretch` silences the "stretch on a custom .pt" warning, so a record can overrule the heuristic that warning comes from. The requirement's *absence* is a different case and deliberately **not** in this list — it is `resize_guess()`, a pure function returning a frozen `ResizeGuess(mode, warning)`, which `_settings_response` turns into `SettingsResponse.unrecorded_resize_mode`. It left the flat list to gain a remedy: `auto` + a custom `.pt` + no record means `resolve_resize_mode`'s letterbox is a guess rather than a fact, nothing can flag it as a mismatch (there is no record to contradict), and `resolve_resize_mode` is too pure to report itself — so the entry carries the mode, the model, and the **two sentences** (`warning`: the diagnosis; `remedy`: how to stop assuming, written to survive being read in a view with no button under it), and the Admin Panel renders a one-click `Record it now` beside them. Prose could not carry that (a remedy is not a string), and reporting it in both places would put the same situation on screen twice, once without an answer. "Both places" means the Admin warning list — the **Live view** renders the same entry too, because it is the screen where weak `far` detections are watched and it is the one screen the mismatch rule cannot serve. The gates live in `resize_guess` so the sentence and the button cannot disagree about when they apply: native-only, matching `resize_mode_resolved`, since a remote backend's workflow holds its own geometry; gated on `auto`, because an explicit `letterbox` is a decision; and the resolved mode is checked rather than inferred, so if the heuristic ever answered something else for a `.pt` this goes quiet instead of contradicting the geometry the detector was built with. The hot set covers more than the fields `Pipeline` re-reads: `conf_threshold` reaches the detector through `set_conf()` and the four `camera_*` controls reach the open device through `CameraCapture.set_controls()`, both routed by `_push_live_settings()` in `main.py`. `PATCH /api/settings?persist=false` applies without writing the file, and `POST /api/settings/save` commits what is in memory — that pair is what lets the Live tab's tuning card drag a slider without every intermediate value becoming the startup config.
- **`hardware.py`** — `probe_hardware()` reports CPU count/RAM via `psutil` and GPU name/VRAM via a lazily-imported `torch.cuda` (same `try/except ImportError` shape as `resolve_device()`).
- **`presets.py`** — `PRESETS` (`low_end`/`mid_range`/`high_end`) are partial settings patches an admin panel can apply wholesale; `recommend_preset()` picks one from `probe_hardware()`'s output using simple CPU/RAM/VRAM thresholds.
- **`roboflow.py`** — `WorkflowClient` posts a base64 JPEG to a Roboflow Workflow (one client serves both `local_api` and `cloud_api` — they differ only by base URL). Retries only timeouts/connect-failures/5xx, never 4xx. Uses `httpx` (already a dependency) rather than `inference-sdk`. The API key goes in an `Authorization: Bearer` header only, and is kept out of `__repr__` and every error message. `find_predictions()`/`find_image_size()` locate the detection list structurally, because workflow output names are chosen by whoever built the workflow.
- **`credentials.py`** — reads `ROBOFLOW_API_KEY` from the environment, falling back to `sidecar/.env`. Deliberately *not* on `Settings`: settings are serialized wholesale to the renderer, so the API exposes only `roboflow_api_key_present: bool` and never the value.
- **`roster.py`** — the app's own copy of the 8 canonical class names, the distance-word predicate, and `class_list_problems()`, the pure verdict over a weight's *own* class list. It exists because a class list is a property of the weights and **nothing else in the runtime knows it**: a `.pt` records no roster, the filename is a convention, and the export that produced it is long gone — so a model trained from a distance-split project loads happily and predicts 24 classes, which the item log then reports as one product under three labels with no error anywhere. That is the other half of the dataset tools' guard (they refuse to *create* such a set; this is what notices one arriving from anywhere else). It cannot import `sidecar/tools/` — `label_classes.SLUG_TO_CLASS` is outside the runtime by design — so the roster and the predicate are a second copy held in step by a **drift guard** (`tests/test_roster.py`), the same hand-mirrored-contract pattern as the settings/WS mirrors. Three findings, worst first and deliberately non-redundant: a distance in a name (the 24-output failure, with the repair named as a retrain, since no setting fixes a head with 24 outputs), names outside the roster, and roster names the model *cannot* predict — that last one is the quiet direction, because nothing it does predict is wrong. It is deliberately silent about the missing-roster finding when a distance is present: technically true, but it restates the same fact in the other direction and would bury the sentence that says what to do. Surfaced on `DetectorProbeResponse.class_warnings` from both probe branches (native and remote — a workflow's model is the one that can change without touching this app), and rendered by the Admin Panel's Test connection result, which otherwise shows only a *count* of classes; a 24-class weight reads there as "24 classes", which looks like a bigger model rather than a broken one. Two further surfaces carry it without anyone pressing anything: the Admin Panel's *Weights on disk* list judges the class list `train_model.py --install` **recorded** beside each weight (`app/models.py`), so a bad one is visible before it is even selected, and the Live view's stats strip carries **`stat-classes`** — the running model's class count plus a count of the findings — which is the one place the count is a readout rather than an input to a verdict, so `24` where an operator expects `8` is legible as a number.
- **`tracking.py`** — `IouTracker` supplies stable `track_id`s for remote backends, which get none from the workflow. Greedy IoU, class-aware (a track never migrates between classes). Pass `expiry_provider` rather than a fixed `expiry_s` when tracking against live settings: `track_expiry_s` is hot-reloadable, so a snapshot desyncs the tracker from `Pipeline` the moment an operator changes it. `reserve_id()` stops a locally-minted id colliding with a server-supplied one.
- **`models.py`** — `installed_models()` answers "what weights could I select, and what does each one need?" by reading `sidecar/models/`, and `GET /api/models` serves it alongside the built-in list. The counterpart to `settings_store.is_custom_model`, which validates model *names* without ever touching the filesystem (so settings tests stay pure) and therefore cannot answer what exists. Exists because the picker was a fixed list in the renderer: a newly trained `models/scanncart-grocery-v2.pt` was valid to the API and impossible to select in the UI, so the one moment the model changed was the one moment the app needed a code edit. Everything it lists is filtered through that same validator, so nothing offered can fail to save; a missing directory is an empty list, not an error. The second half is `read_record()`: the `models/<stem>.json` that `train_model.py --install` writes beside each weight, whose `resize_mode` is the requirement those weights must be run with and whose `class_names` is what they predict — a `resize_mode` of `None` means *not recorded*, never a guess, and a missing, corrupt or hand-edited record degrades to that rather than raising (the Admin Panel loads this on every open, and a value the settings PATCH would reject is dropped rather than presented as a requirement). `class_names` is the read that moves the roster guard *before the run*: `_read_class_names` drops entries that carry no name and answers the empty list for anything absent, and `installed_models` judges a non-empty list with `roster.class_list_problems`, so the panel's *Weights on disk* list carries the same sentences the probe and the Live view do about a 24-class head — while an empty list stays silent, because `class_list_problems([])` would report all 8 roster classes missing, which is a verdict about a class list nobody has seen. It is the second fact only `--install` ever knows (a `.pt` keeps no label set, and the export is the only thing that did), and `record_requirement`'s merge-not-replace is what stops the app-side writer from deleting it. `requirement_for()` is the same record read for the *capture* path instead of the panel: `_default_detector_factory` and `_settings_response` hand it to `resolve_resize_mode`/`resize_guess`, so `auto` **honours** the requirement rather than merely displaying it. `record_requirement()` is this module's *second writer* of those files — the other is `--install`, which knows the requirement because it knows the training run, and this one exists for weights that arrived some other way, where the operator holds the fact; `POST /api/models/record` is its route and the Admin Panel's button is its caller. It merges rather than replaces, because the rest of a record (which dataset version, what `--val` measured) is evidence only a training run can supply, and a whole-file write would delete measurements to add one field; it writes through a temp file + `os.replace` for the same reason `save_settings` does (a half-written record reads as "nothing known", silently discarding the requirement just recorded); it refuses `auto` (a lookup, not a requirement — `resolve_resize_mode` ignores a recorded one, so it would look like the question was answered while `auto` guessed on) and weights that are not on disk (a record describes the file beside it). Its answer is the refreshed `ModelsResponse`, because that list is where the change shows. That is what makes `resize_mode: auto` the correct setting for a locally trained `.pt` — the format heuristic answers `letterbox` for one, which is the wrong geometry for weights trained on a `Stretch to` version, and the failure is silent. `auto_resolves_to` is reported per model for the same reason `hot_reloadable_fields` is: it lets the UI compare the setting against `resolve_resize_mode`'s actual answer instead of reimplementing that rule in TypeScript. With the record honoured it equals the requirement; what it still earns its place for is the *unrecorded* weight, the one case where `auto` really is a format-based guess and the panel has to say which way it falls — the same case `resize_guess` reports, with the one-click remedy beside it, so the guess reaches an operator even with no record to contradict.
- **`cameras.py`** — `list_cameras()` pairs each workable OpenCV index with a Windows device name (PowerShell/`Win32_PnPEntity`, same shape as `hardware.py`) so the Admin Panel can show "1 — Logitech StreamCam" instead of "1". The index↔name pairing is *positional* and can be wrong, which is why each device also reports the resolution it opened at — that is the operator's check. Scanning opens every device and is slow (~30 s), so `GET /api/cameras` caches it and only re-probes on `?rescan=true`, and refuses entirely while capture holds a device.
- **`run.py`** — entrypoint. `pick_port(8765)` falls back to an OS-assigned free port if 8765 is busy, then prints `SIDECAR_PORT=<n>` to stdout — this is the handshake the Electron main process parses to learn where to connect.
- **`../local_inference_server.py`** (outside `app/`) — runs Roboflow's inference server natively so `local_api` works without Docker. Lives in its own venv (`.venv-inference`, `requirements-inference.txt`): `inference` pins numpy/opencv versions that conflict with the ultralytics stack, so installing it into `.venv` breaks `native`. The sidecar never imports it — they only talk over HTTP.

### Dataset tools (`sidecar/tools/`)

Not part of the runtime — the sidecar never imports them — but tracked, because they own the v2 dataset convention in `docs/MODEL_TRAINING.md` §8 and `docs/CAPTURE_CHECKLIST.md`. `clean_v2.py` (ingest → dedupe → stage → upload/retag/wipe/sanity, plus `scaffold`, which lays out a capture tier's `<PRODUCT>/<DISTANCE>/` folders, its README and its exact filing commands from the same `CLASS_MAP`/`DISTANCE_MAP` the ingest uses so a hand-typed folder name cannot be silently skipped — those command paths are rendered `as_posix()` on purpose, because the README is pasted into a shell and on Windows `Path.__str__` gives `sidecar\data\...`, where bash eats the backslash as an escape and `clean --src` then ingests nothing from a directory that never existed. For a held-out tier it also prints the **coverage preflight** (`holdout_gaps` over `staged_coverage` of the earlier sets): the cells with no images outside the session, which are precisely the ones `plan_split --holdout-session` refuses on, asked at scaffold time because by then the fix is a camera decision rather than a planning one. It shares the planner's zero-coverage rule by agreement rather than by re-derivation — a test asserts the preflight's list equals `plan_split.summarize`'s `no_train_cells` for the same staged set — and with nothing staged it reports that it *cannot tell* instead of naming all 24 cells — `TierPlan`s `TIER_A` (session s2) and `TIER_D` (session s3, the held-out acceptance re-shoot, whose commands plan the split *between* `clean` and `upload` because a split cannot be set afterwards); Tier D's cells are derived from the roster × the three distances rather than hand-listed, since it exists to re-shoot what earlier sessions cover). Its **capture session** is load-bearing rather than decorative: `--session` is recorded in the manifest and stamped as a third tag (Roboflow's dataset search has a `tag:` filter and no `batch:` filter, so a batch can group images but not select them), `batch_for_session()` is the single rule naming a session's batches and is shared by `upload`, `retag` and `plan_split` — a planner naming batches differently from the uploader would assign splits to batches that never exist — and `retag`'s read-back verifies the same wanted set it applied rather than the manifest's own tag list, `audit_v2.py` (bucket audit vs. §2), `plan_split.py` (three split plans: A strict-by-batch, B stratified per cell, and `--holdout-session sN`, which puts a whole capture session in `test` and is the only one whose test set is a session `train` never saw; it treats a batch as a *(capture session, class, distance)* bucket, prices a session spread across splits, and prints a session × split table with a verdict — with one session the term is constant across every three-split assignment and the applied plan is pinned unchanged by a test — and it names the `(class, distance)` cells each plan leaves with **no train images**, which is a *reported* number rather than an enforced one because a whole-batch plan over a single session cannot satisfy it: pinning those cells into train would leave nothing held out, so constraining the search would silently trade 70/20/10 away for a number it cannot reach. `--holdout-session` is where the constraint *is* enforceable, so it fails closed — exit 2, no plan written — when holding a session out would leave a cell unlearnable), `label_classes.py` (v1 class names as image metadata, class creation, and `distance_tokens_in()` — the whole-token predicate shared by four checks: `clean_v2.class_list_rows` (what `sanity` prints, so a tainted list blocks a shoot with exit 1), this tool's own check of the **live** project's class list, `generate_version.classes_with_distance` (the same list at the moment of generation, refusing *before* the POST so a bad one spends no version number), and `train_model.check_export`'s check of a generated version's - judged against that **generation's** list rather than one shared roster, since v1 has seven classes and v2 has eight. It exists because a class named `palmolive close` trains one head output per product-and-distance and every box then comes back under a name the app's roster does not contain, with no error anywhere: nothing about a class *name* records that. Whole tokens so "Farmer's Choice" cannot trip it, a list reported as the *fix* (delete the class, move its annotations, regenerate — a version number cannot be reused), and a drift guard in the tests keeps it covering every spelling `clean_v2.DISTANCE_MAP` accepts), `label_progress.py` (labeling/null-annotation state, and the session × split spread the panel renders), `generate_version.py` (generates the Roboflow dataset version from reviewed settings instead of by hand, and `--yes` first refuses a project class list that has a distance in it — checked *before* the POST, because a version number cannot be reused and a distance-split list bakes one class per product-and-distance into the export: fail-closed, exit 2, nothing generated. `sanity` used to say there was no API for it, which is not true of the installed SDK: preprocessing is a one-shot decision that cannot be revised, so it lives in code as `PREPROCESSING` with a `--verify <n>` that reads a version back and diffs it against that block, including refusing `filter-null` because the null-annotated images *are* the hard-negative set. `clean_v2.EXPECTED_RESIZE` imports from it rather than retyping the geometry), `train_model.py` (the local training run and the drop-in that follows it: `--download --version N` fetches the version's export itself by polling the API's export route and extracting the zip, so the whole chain after `generate_version.py` is one command — with `get`/`sleep` injectable because the polling and the failure paths are what need testing, and a zip-slip guard on extraction. `EXPORT_FORMAT` (the API's identifier for the version page's "YOLOv11 PyTorch") is the one value here that could not be verified offline, so a wrong one is recoverable via `--format`. It then checks the export's class list against **its generation's** **before** the GPU runs - v1's seven or v2's eight (`generations.py`) - because a version generated with a short list trains a model whose boxes come back under the wrong label with no error, while a check that judged v1 against v2's eight would refuse a set that is correct, and a guard that cries wolf is how the real mismatch gets waved through. It re-measures how the frames were resized on the same pass (`frame_geometry`: a stretched frame fills its border with content, a fitted one pads with a constant colour) rather than trusting the requirement it is about to record, and it prints which classes another generation declares that this one cannot predict - a *note*, not a problem, and the earliest place the v1/Palmolive fact can surface. It writes its own `data.scanncart.yaml` from absolute split paths rather than trusting the export's relative ones, which assume where the archive was extracted. It reports only the two aggregate metrics a training log actually contains and says so, because `--val` is where the third lives: a separate validation pass that prints per-class recall against `RECALL_FLOOR` (6's 0.85) with the instance count beside each number, in **three** states rather than two — below the floor is a miss, and a class the split holds no instances of is `[SKIP]` rather than 0.000, since "add images of that item" and "add captures to that split" are opposite instructions and a 0 would not distinguish them. Two things in it are load-bearing: recall is read **positionally** against `ap_class_index` (ultralytics builds that from the classes the split has ground truth for, so a class missing from the split shifts every row after it and a `zip(names, box.r)` would print one class's recall under another class's name), and `as_list()` exists because ultralytics answers with numpy arrays, where a one-element `array([0.0])` is *falsy* — `box.r or []` reported "nothing was measured" for a class that had been measured and scored zero, which the live probe caught and a list-based fake could not. `--split` defaults to `test` (the acceptance split; `val` is what the run selected on) and `--val` also reports the **same recall split by distance** — three extra passes, one per distance, each over a file list of the frames carrying that tag (`val-by-distance/*.txt` + a `data.yaml` per distance, so no JPEGs are copied and a row can be traced to its image set) because the per-class floor is a mean over all three distances and `far` is the bucket this dataset exists to fix; the grid prints `-` for a distance holding no instances of a class and `!` for a cell under the floor, the same three states the per-class report has, and `--no-per-distance` skips it (a run with no usable manifest says the breakdown was *skipped* rather than reporting nothing — a section that silently vanishes reads as "every distance passed"). The breakdown is nested in the split's own block and the block is written *after* it, so a stored number can never sit above distance rows from an earlier run; the distance itself is read from the dataset manifest (`distance_map`), because it is a Roboflow **tag** and a YOLO export drops tags — the join has to happen on filenames against the one file that still holds both. And `--install` copies `best.pt` into `sidecar/models/` under the generation's name, refusing to overwrite an existing weight because the picker is keyed by filename — with `latest_run()`/`resolve_run()` finding the newest finished run for a bare `--val`/`--install`, since `run_dir()` answers "where would the *next* run go" and so a bare `--install` used to look for `<name>-2` and fail. It also writes `models/<name>.json` beside the weight: `weight_record()` carries the `resize_mode` the generation requires - v2's from `generate_version.REQUIRED_RESIZE_MODE`, so it cannot drift from the preprocessing that produced its export; v1's frozen at the geometry its own already-generated export was measured to have, because binding it to v2's constant would let a later change to v2 rewrite a requirement about a version that can never be regenerated - because nothing else knows it — a `.pt` stores the training run, not the dataset geometry, the filename is only a convention, and `auto`'s format heuristic answers the *wrong* geometry for these weights. It carries the export's **`class_names`** too, read back from the same `data.yaml` `check_export` judged, and omitted rather than written empty when there were none: this is the one moment the label set is knowable (the export is gone by the next session), and recording it is what lets the app flag a 24-class head from the listing instead of only once it runs. `--val` writes its per-class recall to `val_metrics.json` **in the run directory** rather than in memory, because `--val` and `--install` are separate commands in the documented sequence — and each measurement carries a sha256 of the checkpoint it measured, since re-training into the same `--run-dir` replaces `best.pt` in place and a score belonging to the previous checkpoint must not be attached to the new one (`load_val_metrics` filters on that hash). `write_val_metrics` merges by split rather than overwriting, with `test` first, so measuring the selection split cannot delete the acceptance number. `weight_record(validation=…)` copies the blocks in with the hash stripped — it sits beside the weight it describes, so a copy of that identity inside it would be implied by its location and left wrong by a `--force` replacement of the `.pt` alone — and omits the field entirely when there is nothing measured, so a re-install writes a byte-identical file. The same file is also writable from the app — `POST /api/models/record` / `app/models.record_requirement`, which the Admin Panel's `Record it now` button calls for a weight that never had a run behind it — merging into whatever the tool left rather than replacing it, and recording the geometry the detector is already running rather than changing it. The record is what closes that gap rather than just announcing it: `resolve_resize_mode` takes the requirement as an argument (staying pure and filesystem-free) and prefers it to the heuristic, with `app/models.requirement_for()` doing the read — so leaving `resize_mode` on `auto`, the default, is now correct instead of quietly wrong. `app/models.py` also reads it (`read_record()`, tolerating a missing, corrupt or hostile file, and validating `resize_mode` against `ALLOWED_RESIZE_MODES`) so `/api/models` can report, per installed weight, the requirement **and** `auto_resolves_to` — the latter so the renderer compares against the real rule instead of a second copy of it — and the Admin Panel's Model field lists what is on disk and warns only when an *explicit* value contradicts the record (`resize_mode` is `None`, never a guess, when no record exists, and the panel then names what `auto` gives instead). The same read carries `--val`'s measured recall, so the field can show what the selected weights *scored* beside what they need. Two rules there are not defensive but load-bearing: a block whose `floor` is missing or not a real number is dropped whole (defaulting it to 0.0 would turn every class into a pass), and a `recall` present but outside 0..1 is dropped rather than clamped (no honest pass produces one, so clamping would be this program's invention) — while `recall: null` is *kept*, because that is how "the split held no instances of it" is recorded, and a class the split never asked about must not arrive in the panel looking like a total miss. `recorded` (was a `<stem>.json` found at all) is the one field about the file rather than its contents, and the panel needs it: "installed by the tool, nothing measured yet" and "copied in by hand, nothing known" leave every other field identical, and only one of them is worth telling the operator to run `--val` about. `sidecar/models/` is gitignored with the naming rule *and* the record's format in its tracked `README.md`, so a fresh clone has the convention without the megabytes), `generations.py` (one **spec** per generation - dataset directory, class list, manifest, resize requirement, Roboflow project - which is what turned `train_model.py` from v2's trainer into one trainer for either set: the three fields that differ are exactly the three that used to be constants in it, and a copy of the tool per generation is how their "same" checks drift apart. `manifest = None` means "this generation has no distance axis", not "the file went missing" - opposite sentences, and the reason v1's `--val` reports its per-class table and says so instead of running three passes over an empty map. Its copy of the roster is derived from `label_classes.SLUG_TO_CLASS`; v1's seven are a literal, because a set difference would only be right while the subtraction happened to name the one class v2 adds), `resources.py` (the CPU/RAM/VRAM/disk budget they all run under - now the trainer's too: `--max-use-percent` caps CPU/RAM, the dataloader process count is derived from that instead of ultralytics' default of eight, `torch`'s threads are clamped before anything allocates, and the batch comes from the VRAM share with `--batch` as a ceiling. Measured, that bounds the *batch* and not the card: training yolo11s at 640, batch 8, holds ~5.9 GB of this machine's 8.6 GB, so `--batch 4` is the lever when something else needs the GPU), `workspace.py`. Their tests live in `sidecar/tests/test_dataset_tools.py` and run in the normal pytest pass (`pytest.ini` puts `tools` on `pythonpath`), so a class rename that breaks continuity fails the suite instead of silently mislabeling data.

Code and data are deliberately separated: the tools are tracked, but everything they produce (staged JPEGs, `manifest.json`, split plans, `upload_state.json`, and the `.env` with `ROBOFLOW_API_KEY`) lives in a gitignored **workspace**, `sidecar/data/datasets/`, relocatable via `SCANNCART_DATASET_ROOT` (`workspace.py` is the single source of that path). Paths inside it are relative to each tool's output directory, so the workspace can be moved wholesale but not in pieces. The workspace also holds `v1-source-zips/` — v1's six raw capture archives, 3.9 GB that used to sit inside `.git` (see `workspace.py`'s docstring); nothing in the runtime or the v2 pipeline reads them.

Almost everything is constructor-injected (frame source, detector, clock, logging store) specifically so pytest can run the whole pipeline against fakes with no camera/GPU/network.

### Desktop (`desktop/src/`)

Standard electron-vite three-target layout: `main` (Node, Electron APIs), `preload` (context-bridge), `renderer` (React, sandboxed, no Node access).

- **`main/sidecar.ts`** — `SidecarSupervisor` spawns the sidecar (`spawnFn` is injectable for tests), parses `SIDECAR_PORT=<n>` off stdout line-by-line, and forwards stderr so uvicorn's own log pipe never fills up and blocks the child. Reports the port and unexpected exits via callbacks.
- **`main/index.ts`** — resolves the sidecar's python/script paths relative to the packaged app (overridable via `SIDECAR_PYTHON`/`SIDECAR_SCRIPT` env vars), starts the supervisor on `app.whenReady()`, exposes the current port to the renderer over `ipcMain.handle('sidecar:port', ...)`, and kills the sidecar child on `before-quit`.
- **`preload/index.ts`** — exposes `window.api.getSidecarPort()` via `contextBridge`; that's the *only* main↔renderer bridge. Everything else (REST calls, WebSocket) goes straight from the renderer to `127.0.0.1:<port>` — Electron IPC is used only to learn the port.
- **`renderer/src/lib/ws.ts`** — `createStreamClient` wraps `ws://127.0.0.1:<port>/ws/stream` with auto-reconnect (so the UI tolerates the sidecar not being up yet) and a structural `WSLike` type so tests can inject a fake WebSocket.
- **`renderer/src/lib/api.ts`** — thin REST client (`health`/`start`/`stop`/`getLogs`/`getSettings`/`updateSettings`/`getSystemInfo`/`getPresets`/`applyPreset`/`getDatasetStatus`) hitting `http://127.0.0.1:<port>/api/*`; `request<T>()` supports `GET`/`POST`/`PATCH` with an optional JSON body.
- **`renderer/src/lib/settingsFields.ts`** / **`lib/settingsDefaults.ts`** — client-side mirrors of the sidecar's `ALLOWED_MODELS`/`ALLOWED_DEVICES` and `Settings` defaults, kept in sync by hand (same tradeoff as the WS contract below) — drives `AdminPanel`'s form and its "Restore Defaults" action. The server's `hot_reloadable_fields`/`restart_required_fields` on `SettingsResponse` remain the source of truth for which fields require stopping capture.
- **`renderer/src/hooks/useSidecarStream.ts`** — the core state hook: wires REST + WS into React state, dedupes detections into a session item log by `track_id` (one row per item, keeping the max confidence seen). On WS open it seeds from `GET /api/logs`, but only when `statusState === 'running'` — this is reconnect recovery, not "load history on launch"; a fresh/idle app starts with an empty log, and `start()` resets the dedup set for a new session. Status messages are read as: the `state` always becomes the toolbar's state, and **any non-empty `detail` raises the error banner** — not only one whose `state` reads `error`. That is the two shapes the sidecar has for the same field (a capture dying mid-session, and the stored reason for one that died before this client connected, where `state` is legitimately `idle`), and `detail` only ever carries an error explanation, so gating on the state would just lose the recovered case. The dismissal is the banner's own button and is not remembered across reconnects, because the sidecar still has the same reason.
- **`renderer/src/hooks/useDatasetStatus.ts`** — reads labeling progress for the Admin Panel. Loads **once**, not on a timer: the sidecar serves a snapshot file that only changes when the tool is run by hand, so an interval would refetch identical bytes and imply a liveness the data does not have. Exposes `refresh` for a button instead, and the panel renders `age_seconds` so the operator can see the staleness.
- **`renderer/src/hooks/useSidecarSettings.ts`** — fetches settings/system-info/presets on mount and polls `GET /api/health` (reusing the existing endpoint rather than a second WebSocket) to track `captureState` for save-gating. Exposes `update`/`applyPreset`/`restoreDefaults`.
- **`lib/resizeMode.ts`** — `resizeModeMismatch(mode, selectedModel, installed)` is the one place the "settings contradict the weights' record" comparison lives, and both views call it: `AdminPanel` passes the *pending* draft value (so the warning clears as the fix is typed) and the Live view passes the running one. It resolves `auto` through the sidecar's own `auto_resolves_to` rather than reimplementing `resolve_resize_mode`, which is why `auto` can never be the mismatch, and it answers `null` for a weight with no record (a hand-copied file is not mismatched with anything, and a warning no setting could clear is worse than none). Two copies of this comparison would eventually disagree about what "mismatched" means.
- **`hooks/useResizeMismatch.ts`** — fetches exactly the two things the question needs (`/api/settings` and `/api/models`), once, with no polling, and returns the mismatch or null. Deliberately not a second `useSidecarSettings` (that hook also loads system info, presets and a camera profile, two of which are device queries, and `CameraTuning` in the same view already fires it — `apiFactory` goes in the effect deps rather than a ref, matching that hook). A failed load leaves `null`: an unreachable sidecar is already visible in the toolbar, and a verdict that cannot be computed must not send the operator to change a setting that is not the problem.
- **`views/LiveView.tsx`** — renders the JPEG preview, detection-box overlay (`lib/overlay.ts` converts normalized boxes to CSS percentages), fps/latency stats strip, and the item log; Start/Stop drives `start()`/`stop()` from the hook. It also carries **`live-resize-mismatch`**, the same resize warning the Admin Panel's Model field shows, gated on `running` and not dismissible: the claim is about the frames and the log on screen, which is not true of an idle view (where the field is one click away in Admin and already says so), and dismissing it would hide the only explanation for detections that are weaker than the model can do. Beside it sits **`live-assumed-geometry`**, the other resize case and the softer one: nothing contradicts anything (the settings are on `auto`, the documented answer), but no record says what geometry these weights were trained at, so `auto` is guessing — and `settings_store.resize_guess`'s entry is the only thing that can say so, since `resizeModeMismatch` needs a record to contradict. Same gate for the same reason, and the two are mutually exclusive by construction (one needs a record to disagree with, the other needs its absence), so they never stack. It renders the entry's `warning` **and** `remedy` verbatim and carries the **same record-it-now button** the Admin Panel has — safe mid-capture, because the mode written is the one `auto` already resolved to, so the detector is not disturbed; that is what makes the view switch unnecessary. `record()` lives in `useActiveWeights`, taking the model and the mode from the entry the sidecar named (so no caller can write something else), re-reading both endpoints after the write, and setting `justRecorded` only when the refreshed answers no longer report the assumption — so the banner clears because the server says the fact is recorded, not because a click happened, and a failed write simply keeps it with its button. The slot the banner vacated then shows a green **`live-recorded`** line whose sentence is shared with the Admin Panel's acknowledgement (`lib/resizeMode.ts`'s `recordedConfirmation`) and whose mode is read back off the refreshed listing rather than echoed from the click. Beside it, ungated by `running`, the stats strip carries **`stat-requirement`**: what the record says these weights were trained at (`requirement (recorded)`) or, dim italic like the recall tile, that nothing recorded it (`requirement (assumed)`) — the banner's fact while idle, which is when someone is deciding whether to start. **`stat-classes`** is the last tile, and the one fact on this strip that describes the *running* model rather than the configured weights: the class count the sidecar reported on the stream, labelled `classes · roster ok` or `classes · N findings` with the sidecar's own sentences in the title, amber when there are findings. It is deliberately *not* inside the gate that hides the geometry tiles for a remote backend — a workflow declares its classes too, and there is no local model description to hide behind — and it renders nothing until the sidecar has read a model's vocabulary, because `0 classes` would be a claim about a head that has not spoken yet. The division from the banner above is the one the geometry tiles draw: the banner is the problem (only when there is one), the chip is the state (always, once known), which is what makes a healthy `8` as visible as a broken `24`. The side rail also hosts `components/CameraTuning.tsx` — the camera controls that can change while capture runs, plus calibration. `SETTINGS_GROUPS[].home` decides whether a group renders here or in `AdminPanel`; it is one list filtered by both views, so a field cannot appear in both or neither.
- **`views/AdminPanel.tsx`** — hardware info, a dataset **labeling worklist** (the cells still waiting for a box, ranked biggest-first from the local snapshot, rendering the "run the tool" instruction instead of zeros when there is no snapshot, with an explicit Refresh and a staleness line; the order is the sidecar's and the panel does not re-sort it, because the order *is* the instruction — one place deciding priority), plus a separate **capture gap** block listing the Tier A cells still short of their target — kept apart from the class table because those cells are waiting for the camera rather than a label, preset picker (recommended preset highlighted), and a form over the 10 settings fields with inline tradeoff guidance and hot-reload/restart-required badges. Edits are held in local `draft` state until Save; Save is disabled (with a warning) if the pending diff touches a restart-required field while capture is running.
- **`components/AppShell.tsx`** — owns Live/Admin view-switching state (`useState`, no router dependency) and renders a small nav.
- **`App.tsx`** — polls `window.api.getSidecarPort()` until non-null (the sidecar reports its port asynchronously after spawn), then mounts `AppShell`.

### Testing conventions

- Sidecar tests always use fakes (`FakeFrameSource`, injected detectors/clocks) — never a real camera or GPU. Don't add tests that assume Ultralytics/OpenCV hardware is present.
- Desktop tests inject `spawnFn`/`wsFactory`/`apiFactory`/`streamFactory` rather than mocking modules — follow that pattern (see `sidecar.test.ts`, `useSidecarStream.test.tsx`) when adding new injectable dependencies.
- The WS message contract (`FrameMessage`/`StatusMessage`/`Detection`) — and now the settings contract (`SettingsPayload`/allowed models/allowed devices/defaults) — are duplicated by hand between `sidecar/app/schemas.py`+`settings_store.py` (Pydantic/Python) and `desktop/src/renderer/src/lib/api.ts`+`settingsFields.ts`+`settingsDefaults.ts` (TS). There's no shared schema generation, so keep them in sync manually when either protocol changes. That now includes `ALLOWED_BACKENDS`, and `MIN_TRACK_EXPIRY_S_BY_BACKEND` (mirrored as `minTrackExpiryS()`) — the per-backend floor below which a slow round trip can expire a stationary item and log it twice. That now includes `FieldGroup.home`, and the four `camera_*` `FieldMeta` bounds (which mirror `SettingsUpdateRequest`'s `ge`/`le`). That now includes `CameraProfile.measured`/`sweep_version` and `ControlSupport.autofocus`, mirrored by `MeasuredControl` and the matching fields on `CameraProfileResponse` in `api.ts`. That now includes `StatusMessage`'s `class_names`/`class_warnings` pair — the running model's own vocabulary and the sidecar's verdict on it, both rendered as they arrive and neither re-derived here, since the roster has one owner — and the empty list's meaning on both sides (`not known yet`, never `predicts nothing`). The resize-mismatch *rule* is also shared rather than mirrored — it lives once in `desktop/src/renderer/src/lib/resizeMode.ts` and is called by both views, since a second copy would be a second answer to the same question. That now includes `UnrecordedResizeMode` (`model`, `resize_mode`, and the split `warning`/`remedy` prose, which two views render and only one can act on) and the `recordResizeMode()` client method, which is how the panel's button reaches `POST /api/models/record`; the mode is read from the sidecar's entry rather than derived in the renderer, and the acknowledgement is read back off the refreshed weights list rather than remembered, so nothing in the panel re-derives either fact. `useActiveWeights` carries that entry as `unrecorded` for the Live view, taken from the same `/api/settings` read as the geometry and the score so the banner and the stats strip cannot describe two different configurations; it also carries the record's own mode as `required` (the evidence, where `unrecorded` is its absence) and the one write that can change either — `record()` with its `recording`/`justRecorded` state — so the two views' buttons are one implementation rather than two. That now includes `ModelsResponse` (stock weights plus `InstalledModel` records — names, the recorded `resize_mode` requirement, `auto_resolves_to`, provenance, `recorded`, and `validation`: `ValidationRecord`/`ClassRecall`/`DistanceRecall` for what `--val` measured, the last of which is a distance's slice of a split — the same classes over a different image set, `images` being frames where `instances` is boxes, and carrying no `floor` of its own because the block it hangs under already states the one they were judged against, whose `recall: null` means *the split held no instances of it* and must stay distinct from `0.0` all the way to the pixels; labels stay in `settingsFields.ts`, only the *values* travel, so a new model needs no renderer edit. The hook exposes both the names the picker needs and the records the panel needs, deriving one from the other rather than shipping two lists that could disagree), `DetectorProbeResponse`'s `sent_size`/`reported_size` (the remote probe's geometry pair, where `reported_size: null` means the workflow reported nothing and the coordinates were *assumed*, so the panel renders three states rather than a comparison of two numbers), `DatasetStatusResponse`'s fields — including `DatasetTierACell`/`DatasetSessionProgress`/`DatasetBacklogCell` and the `tier_a_*`/`sessions`/`labeling_backlog` blocks the panel renders (the backlog's `background` flag is a field rather than a test on an empty `distance`, because that row differing is a fact about the dataset rather than about a string) — and the one contract the file boundary cannot cover: the snapshot's own shape, which `label_progress.py` writes and `app/dataset_status.py` reads — both tolerate a malformed field rather than raising, because the writer is a separate program.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
